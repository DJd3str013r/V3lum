# Backlog - p1-G09-1

Batch p1-G09-1: ransomlook (P196), ransomware_live (P197), ransomfeed (P356), crypto_sanctions (P205,
split into crypto_sanctions_offline and crypto_sanctions_onchain) and tron_explorer (P207). Every item
below is a final condition that is met only in part, with the reason and what unblocks it.

| item | reason | unblock condition |
|---|---|---|
| P196 cond 1 - index from `/api/posts/period/{d1}/{d2}` | The dataset manager only downloads registered static URLs, so the daily index uses `/api/last/30` (every post discovered in the last 30 days, ~1 MB on 2026-11-26), which is the static-URL form of `/api/posts/period/{today-30}/{today}`. | Core dataset manager accepts date-templated URLs (`{today}`, `{today-30}`) in `register_dataset`; switch `ransomlook_recent_posts` to the period endpoint. |
| P196 cond 3 / P357 - shared ransomware helpers in core | The victim-name normaliser, group-alias normaliser, `match_claim`, `report_claims`, `actor_profile` and the 'not listed' wording are shared by P196, P197 and P356 but live in `v3lum/modules/darkweb_ransomware/ransomlook.py`: batches cannot create core files. P357 (telegram watch) needs them too. | Core adds a home for them (e.g. `v3lum/core/ransomware.py`); ransomlook, ransomware_live, ransomfeed and the rule `g09_ransomware_corroborated` import from it. |
| P196 cond 5 / P356 cond 2 - one finding per victim across trackers, counted once in the score | Each tracker emits one finding per victim claim (re-posts within 3 days collapse); cross-tracker grouping is the correlation rule `g09_ransomware_corroborated` ('corroborated by N trackers': victim + group alias + date +/- 3 days). Grouping findings into one card and scoring the group once is P335/P302 work, not built yet. | P335 finding groups and P302 scoring read the rule's correlation key (victim + group alias + first date) and count the group once. |
| P196 cond 6 / P356 cond 3 - 'victims who are natural persons' | The trackers do not say whether a victim is a person. `ransomlook.is_probably_organisation()` is a fail-safe heuristic: description text is kept only with positive evidence of an organisation (organisation word or legal form, a domain, digits, an acronym, a single-token brand); every other victim (e.g. 'Given Family') gets none. A real person classifier is out of scope. | A council-approved person/company classifier (or a tracker field) replaces the heuristic. |
| P197 cond 4 - recentvictims for watch | `/v2/recentvictims` (noncommercial, research only) and PRO `/victims/recent` (keyed, licence-gated) are not registered datasets: `v3lum data update` has no licence gate and cannot send a key header, so a registered download would bypass P197 cond 1-2. Watch and supplier screening use the RansomLook and Ransomfeed indexes meanwhile. | Core dataset manager checks the source's licence/terms (policy gate) before a download and supports keyed downloads (header from the key registry, redacted); then register `ransomware_live_recent` under `ransomware_live.pro`. |
| P197 cond 7 / P207 cond 4-5 - PRO and Tronscan success fixtures | No team key exists for ransomware.live PRO or Tronscan, and ransomware.live corporate use also needs the owner's written approval (T&C s.5.2). PRO shapes are tested from the swagger description and Tronscan fields from its API documentation; the 401 answers without a key are recorded (`pro_needs_key.json`, `tronscan_needs_key.html`, live-checked 2026-11-26). | Legal records the ransomware.live approval in `licence_allow` and the key plans (`key_plans`); the team keys are configured; success fixtures are captured and the parsers re-checked. |
| P197 cond 6 - ransom-note contacts | The provider is sensitive (A4): the core sanitizer's second net drops every `content` field before the module runs, so the ransom-note text (and its onion/e-mail/qTox contacts) never arrives. The module spends no request on it and records source `ransomware_live.pro_notes` as SKIPPED 'policy'. | Core sanitizer lets a sensitive source declare a field that is read by a module-side extractor before scrubbing (contacts only, the text never stored), or exempts the attacker-authored note text; then the existing `note_contacts()` path is enabled. |
| P197 cond 6 - group IOCs of a sensitive provider | The second net drops keys named `ip`, and hex hashes next to e-mail keys, so IP and some hash IOCs of `/iocs/{group}` never reach the graph; domains, URLs, e-mails, onions and wallet IOCs pivot (hostile, `expand=False`). | Core sanitizer allow-list overrides for indicator feeds of sensitive providers (attacker infrastructure is not victim data). |
| P197 cond 6 - qTox contacts | There is no entity type for a Tox ID: qTox IDs from ransom notes are counted in `ransomware_group_profile.ransom_notes.qtox_ids` and not pivoted. | Core entity type for messenger IDs (e.g. `tox_id`) with a validator; then hostile pivots with `expand=False`. |
| P205 cond 1 - list commit per match | raw.githubusercontent.com does not expose the commit of the `lists` branch: every match keeps the list date (the local copy's fetch date) and the list SHA-256 instead. | Core dataset manager records the upstream commit of GitHub-hosted datasets (e.g. one `api.github.com/repos/{owner}/{repo}/commits/{branch}` call per refresh) in `DatasetInfo`; the module adds it to `hits[].list_commit`. |
| P205 cond 5 - SDN entity and programme of a list hit | The 0xB10C lists carry addresses only. Citing the SDN entity and programme needs the OFAC SDN data: `SDN_ADVANCED.XML` redirects to a presigned S3 URL whose `X-Amz-*` query parameters must not reach the cache, logs or evidence. The finding links OFAC Sanctions List Search meanwhile; the on-chain/REST path names the entity when Chainalysis REST (key) answers. | Either core redacts presigned S3 parameters (`X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`) everywhere, or sanctions_lists (P219, batch p1-G10-1) exposes the parsed SDN `Digital Currency Address - <ASSET>` remarks with entity and programme; crypto_sanctions_offline then cites them per hit. |
| P205 cond 6 - 'the sanctions tag comes only from this module' | The GoPlus module belongs to another batch: this batch cannot stop it from setting a sanctions flag. The rule `g09_sanctions_non_authoritative` adds an INFO line 'Sanctions flag from a non-authoritative source' to a wallet whose `sanctions` tag or `sanctioned=True` comes from any other module (e.g. GoPlus), and stays silent when crypto_sanctions_offline or crypto_sanctions_onchain confirms it. | The GoPlus owner maps its `sanctioned` flag to an attribute (never the `sanctions` tag); optionally a vocab/registry rule restricting the `sanctions` tag on crypto nodes to crypto_sanctions_* and sanctions_lists. |
| P205 cond 2 - custom `eth_rpc` endpoints | The setting accepts only https URLs whose host has a provider entry (tier, terms): the default PublicNode host is registered; another operator is refused with a clear 'could not verify' error rather than sent the wallet. | A provider fragment per approved RPC operator (tier and ToS recorded); no code change needed. |
| P207 cond 3 - counterparty labels | Labels come from crypto_address_labels (P358, another batch): `top_counterparties[].label` is `None` until it exists; Tronscan labels are read only for the investigated address with the `tronscan` key. | P358 lands; a correlation (or this module through a shared label index) fills the labels of transacted_with nodes. |
| P207 - transaction count without Tronscan | TronGrid has no total transaction count: without the `tronscan` key the summary shows `transfers_seen` (TRC-20 transfers on the two pages read) and no `tx_count`. | The team `tronscan` key (see above). |
| P207 cond 5 - throttled-answer fixture | A real throttled answer is not recorded (no deliberate hammering of TronGrid): the `{"Error": "request rate exceeded ... suspended"}` marker, `{"success": false}` bodies and HTTP 429 are tested inline. | The first throttled answer seen in normal use is captured (scrubbed) as `tests/fixtures/tron_explorer/throttled.json`. |
| P356 cond 1 - core safe XML helper | No core safe-XML helper exists yet: the RSS is parsed with an expat stand-in that refuses every DTD, entity and external reference (`ransomfeed.UnsafeXML`). | Core ships a safe XML helper (batch p1-G10-1 builds one for sanctions_lists); ransomfeed switches to it. |
| P356 cond 1 - actor-card endpoint | The final condition names `/gang/{group}` for actor cards, but on 2026-11-26 `/gang/{group}` returns the group's claim rows and `/ganginfo/{gang}` returns the card (name, description, leak-site locations, reference links): the module calls `/ganginfo`. | None (documented deviation; re-check if the API changes). |
