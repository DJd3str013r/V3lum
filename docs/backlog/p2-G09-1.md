# Backlog - p2-G09-1

Batch p2-G09-1: deepdarkcti_index (P198), onion_lookup (P199), chainabuse (P204), goplus_security (P206,
GoPlus + Honeypot.is) and walletexplorer (P208). Every row is a final condition met only in part, with the
reason and what unblocks it. No LIGHT/ACTIVE variant was requested by these proposals.

| item | reason | unblock condition |
|---|---|---|
| P199 cond 2 - `is_banned_onion()` as a core safety filter applied by every module | Batches cannot edit `v3lum/core`: the Ahmia banned-list dataset (`ahmia_banned_onions`) and `is_banned_onion()` / `add_banned_finding()` live in `v3lum/modules/darkweb_ransomware/onion_safety.py` and are applied by deepdarkcti_index and onion_lookup only. Other modules that display, store or enrich onions (ransomlook, ransomware_live, ioc_extract, pivot links...) do not apply it yet, and the engine still stores/renders the entity value of a banned onion typed or pivoted into the case. | Core moves the dataset and the filter into core (e.g. `v3lum/core/onion.py`) and applies it in the engine (before scheduling modules on an onion), the graph/store (keep only the md5) and the renderers/exports ('details withheld'); onion_safety then re-exports the core names. |
| P199 cond 4 - DNS layer refuses `.onion` names | The core HTTP layer refuses `.onion` hosts outside a LIGHT Tor `proxy_light` (WP11, tested in tests/modules/test_onion_lookup.py), but `v3lum/core/dns.py` `Resolver.query` would send an onion name to the configured DoH resolvers (tracked by the non-strict xfail `test_core_dns_refuses_onion_names`). The modules of this batch never resolve onions. | Core DNS refuses names under `.onion` (RFC 7686) with a could-not-verify answer and no request, outside a configured Tor profile; the xfail test then passes. |
| P199 cond 5 - Ahmia onion index list | Not downloaded by design: Ahmia's ToS (25 Sep 2026) forbid replicating the service without permission; Ahmia search stays manual (`manual_link` https://ahmia.fi/). | Ahmia's written permission recorded; then a 'license' dataset with a licence_allow entry. |
| P198 cond 3 - repository commit date per list | raw.githubusercontent.com sends no Last-Modified, so the list date comes from the GitHub REST commits API (registered datasets `deepdarkcti_index_commit_<list>`, source `github.deepdarkcti_index_commits`). From the build session every api.github.com request was refused by the session's own GitHub proxy (HTTP 403, live run 2026-11-26), so the commit path is verified offline only; without it the wording reads 'list date unknown, fetched <date>'. The stored commits answer also holds the maintainer's name/e-mail (only the date is ever read). | Live check from the production egress (keyless 60 requests/hour; seven a week); core dataset manager records the upstream commit/date of GitHub-hosted datasets in `DatasetInfo` (same request as p1-G09-1) so the commit datasets can go. |
| P198 cond 2 - shrink check against the previous good copy | The validators refuse HTML, empty tables and parses below the row/entry floors (~40% of the 2026-11-26 counts), but a `register_dataset(validate=)` callable sees only the new file, so a >50% shrink versus the previous copy is not detected. | Core dataset manager passes the previous copy (or its row count) to validators, or exposes a doctor hook for dataset health. |
| P198 cond 2 - parser shared with P357 | `parse_markdown_table` / `parse_ddc_list` are public in `v3lum/modules/darkweb_ransomware/deepdarkcti_index.py`; telegram_channel_watch (P357, batch p2-G09-2) downloads its own copy of the two Telegram lists and keeps its own parser. | P357 imports the parser from deepdarkcti_index (or the core gives it a shared home). |

| P204 cond 5 - keyed success/empty/401 fixtures | No team key: `reports_ok_synthetic.json` and `reports_empty_synthetic.json` are synthetic (documentation values, shape from the research record and docs.chainabuse.com); the 401 body is the real keyless answer. | P204 cond 4 - corroboration above medium | The module never goes above medium; the rule `p2g09_chainabuse_corroborated` raises the case to HIGH with sanctions (crypto_sanctions_*), GoPlus flags, a ransomware finding of another module or a scam/hack/market explorer label. No Ransomwhere module exists yet. | A Ransomwhere module lands (its 'ransomware' findings already count). |
| P206 cond 5 - Honeypot.is | Registry review 2026-11-26: anonymous operator (no legal entity or privacy policy; API terms of 2023-12-05 name only 'honeypot.is') -> tier `unknown` (`v3lum/data/providers/honeypot_is.json`), so Honeypot.is is not queried and its source is not declared (an unknown-tier source would also take goplus_security out of the default set, A3).
