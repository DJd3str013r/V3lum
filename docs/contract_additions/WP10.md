# Contract additions - WP10 (wave 2)

Storage v2: keyed HMAC pseudonyms (A4), provider quotas (P334), the shared per-host limiter with the
LIGHT/ACTIVE ceilings (A7), schema migrations (AR04), one purge routine with legal hold and
tombstones (A10) and file permissions (AR03). Nothing of the frozen guide changes: `ctx.http`,
`ctx.quota_remaining()`, `Module.daily_quota`, the provider `quota` block and every exception keep
their documented meaning; this file only adds names and states the enforcement that the guide
announced as "provider quotas (wave 2)".

## Details

### Keyed HMAC pseudonyms (A4) - `v3lum.core.hmacid`

* The installation secret is `~/.v3lum/secret.key` (32 random bytes, 0600, created atomically on
  first use, never exported; a loosened mode is tightened). Pseudonyms are stable for one
  installation and differ between installations, so a guessed value cannot be tested without the
  secret (unlike a plain SHA-256).
* Pass **normalized** values (`Entity.value`); the type may be an `EntityType` or its value string.
* Modules may use `hmac12`/`hmac_hex` where they need a stable key for a value they must not keep in
  clear (e.g. a dedupe key in `ctx.state`, which refuses personal values). Example:
  `ctx.state.set("seen", {hmacid.hmac12(entity.type, entity.value): ctx.now().isoformat()})`.
* `PSEUDONYMISED_TYPES` = PERSONAL_TYPES + SECRET_TYPES + `text_blob` + `file`: in search indexes
  these appear only as `'<type>:#<hmac12>'` (`pseudonymize_key(key)`); other entity keys stay as they
  are (a token or card number never sits in an index in clear, even when a caller forgot to redact).
* A `secret.key` owned by another user is refused (`RuntimeError`): whoever planted it could reverse
  the pseudonyms (a V3LUM home in a shared directory).
* Tests: `tests/test_hmacid.py`.

### Provider quotas are enforced (P334) - what fragment and module authors can rely on

The provider `quota` block of a fragment (`scope`, `hour`, `day`, `month`, `rate_per_second`,
`burst`, `published`, `evidence_url`, `safety_margin`) is now enforced by the core before every
request to one of the provider's hosts (`ctx.http`, all modules of the provider share one counter):

* budgets per UTC window = `floor(limit x safety_margin)` (at most 80% of the published limit);
  `scope: "egress_ip"` budgets are global per installation and egress (never multiplied by keys,
  proxies or Tor); `scope: "key"` plans are counted per key name of the provider's `keys` block;
* the last 20% (`SEED_RESERVE`) of every window is kept for analyst-typed seeds: requests of pivots
  at depth >= 2 (`RunInfo.priority == 'pivot2'`) never consume it;
* `rate_per_second`/`burst` form a token bucket at `rate_per_second x safety_margin` (the same 80%
  default as the windows: VirusTotal's published 4/min becomes one request every 18.75 s): the
  reservation takes the provider's next slot and **returns** the wait; refused requests never take
  a slot. The HTTP client spends that wait on the runtime clock within the run deadline (wave-2
  integration: `HttpClient._fetch` consumes it before every request to the provider's hosts). The
  longest wait accepted is `max(RATE_WAIT_MAX, one provider interval)`: one paced slot (18.75 s for
  VirusTotal) is always waited when the run deadline allows, `RATE_WAIT_MAX` caps only queueing
  beyond it; a longer wait or one the run has no time left for is RATE_LIMITED 'could not verify
  now' (never an absence). Every request of the provider shares the bucket - dataset downloads
  (`ctx.data`) of the provider included - so a module making two requests to a slow provider needs
  a `timeout` above one interval; fragment authors may still set `http_profile.min_interval` for
  the per-host limiter;
* a provider's own quota signal (a P321 error marker or provider marker classified `quota`) wins
  over the counters until the provider's shortest budget window resets (the UTC day without a
  block): every later request of the same run to that provider is refused before it is sent, and
  the signal is recorded in the quota DB, where it stops the pivots of other runs and processes
  (a team sharing `quota_db_path`); an analyst-typed seed of another run still gets one attempt -
  the provider's latest answer is the truth and re-signals when still exhausted (this also keeps
  separate `run_module` calls in one test independent, as the guide's worked example expects); a
  `rate_limited` classification backs the provider off for the rest of the run (memory only); no
  signal lasts longer than `MAX_SIGNAL_DAYS`;
* refusals raise the documented exceptions from inside `ctx.http`: `QuotaExceeded` (Status.QUOTA,
  'could not verify') and `RateLimited`; modules let them propagate as before (partial results are
  recovered by the engine). Exhaustion never triggers a LIGHT/ACTIVE alternative, another account
  or another egress; the engine defers the lookup (`cases resume`);
* DoH (`ctx.dns`, the `DOH_PROVIDERS` and public DoH hosts) is never charged.
* `Module.daily_quota` stays the fallback for providers without a quota block (per-module counter,
  unchanged).
* Tests: `tests/test_quota.py`.

### LIGHT/ACTIVE ceilings (A7) - `v3lum.core.limiter`

The constants above are the hard ceilings the HTTP client and the socket connector enforce (WP11):
`max_rate` of a LIGHT module stays <= `LIGHT_MAX_RPS`, of an ACTIVE module <= `ACTIVE_MAX_RPS`;
modules, provider profiles and scope files can only lower them. The shared per-host limiter always
reserves a slot (also for `min_interval = 0`) and applies the largest interval declared for a host
by any module, profile or opsec floor (LIGHT 1.0 s, ACTIVE 0.1 s). Tests: `tests/test_quota.py`
(limiter section).
