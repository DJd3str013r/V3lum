# Contract additions - WP12 (wave 2)

Declarative JSON/NDJSON/CSV/RSS/XML/HTML-JSON collectors (P331): the spec compiler announced by the
frozen guide (section 17 schema `v3lum.spec/1`, section 25 "Arriving later":
`v3lum.core.specs.compile_spec`). Nothing of the frozen guide changes: the section 17 fields keep
their names and meaning, compiled classes carry `spec_origin` as the guide and the registry contract
test (section 22) expect, and every Module name keeps its behaviour. This file lists the names WP12
adds and the precise semantics of the schema fields. The file format reference is
[v3lum/data/specs/README.md](../../v3lum/data/specs/README.md).

Who needs it: **spec authors** of the module batches (bundled specs in `v3lum/data/specs/` with
fixtures in `tests/fixtures/specs/<name>/`), analysts writing **user specs** in `~/.v3lum/specs`,
**WP25** (doctor: health checks, `HealthState`, `specs.disabled()`), **WP29** (docs/notices) and
**WP30** (plugin hardening reuses the AR12 ownership rule).

## Details

### Compiled classes

`compile_spec` validates the spec (`SpecError` with every problem), then builds
`Spec_<name>(SpecModule)` whose class body declares identity, `accepts`/`produces`, `run_on`,
`terms`, `opsec = Opsec.PASSIVE`, `disclosure = 'third_party'`, literal `hosts`, `provider`,
`sources`, `access_model`, keys, `max_requests`, `expected_latency`, `min_interval`, `cache_ttl`,
`absent_statuses`, `error_markers`, `manual_link`, `default_enabled`, `requires_egress` and
`spec_origin` (`'bundled:v3lum/data/specs/<name>.json'`, `'user:<path>'` or the caller's label), and
registers it with `@register`: the contract lint, the derived attributes, the policy gate, quotas,
the sanitizer and the registry contract test apply unchanged. A name taken by another module - or by
another compiled spec: every compiled class is `Spec_<name>`, which `@register`'s same-class rule for
re-imported module files would otherwise accept - is a `SpecError` ('duplicate module name').
`health_check()` returns the spec's `HealthCheck(etype, value, expect)`. Compiled classes carry no
code of their own (their `run`/`applies`/`health_check` are `SpecModule`'s), which `@register`
checks, so a hand-written module cannot pose as a compiled spec to replace its module tests by spec
fixtures.

### Loading (`module.load_modules`)

`load_modules()` calls `specs.load_specs()` after importing `v3lum.modules` and the plugin
directories; a crash of the loader itself is recorded as `spec:*`, never raised. Bundled specs are
always compiled; user specs are user content like the plugins and are compiled when the caller loads
its user directories (`extra_dirs` given, or `user_specs=True`), so a bare `load_modules()` (tests,
tools, collection of the registry contract test) never reads `~/.v3lum`. Bundled specs need
`tests/fixtures/specs/<name>/{ok.*, error_in_200.*, expected.json}`; user specs need the same files in
`~/.v3lum/specs/<name>/` and load only when the directory, the spec file and every fixture pass
`paths.insecure_reasons` (owned by the current user, not group/world-writable; AR12). Every spec is
linted with `lint.lint_data_file` (P327) - the file at load and the document inside
`validate_spec`, so `compile_spec` refuses lint issues on every path - and its request URL with
`lint.forbidden_probe`. User specs never shadow a module or a bundled spec. A reload unregisters the
specs of the previous load first. Each file loads in isolation: an unreadable, non-UTF-8,
oversized (> 512 KB), absurdly nested or otherwise broken file is reported and the others still load.
Load-error keys: `spec:<name>` for a refused spec whose (well-formed) name nothing else uses;
`spec:<path>` for an unreadable file, a refused directory, a file whose `name` differs from its stem
and a file whose name is already taken by a module or another spec; `spec:*` (loader crash).
`policy.decide` (POL-02) skips a *registered* class whose name carries a `spec:<name>` error, so a
refused file never reports under the name of a registered class (a colliding user spec must not
disable the module it collides with).

### Schema semantics fixed by the compiler (section 17 fields)

* All section 17 fields are **required** (declared explicitly; `null`, `[]` or `""` where allowed).
  Optional additions: `reference`, `tags`, `notice`, `requires_egress`, `notes`; `x_*` and `$comment`
  are ignored. `disclosure` must be `third_party`, `opsec` `passive`, `max_requests` 1..5.
* `request.url`: `https://` + one literal declared host + path/query; placeholders `{value}`
  (percent-encoded, `:`/`@` kept), `{value_q}` (nothing kept), `{value_qp}` (`quote_plus`),
  `{domain}`, `{user}`, `{b64}` in path/query/params only, type-checked against `accepts`; `GET`
  only; headers literal or `{key:<name>}` (optionally prefixed `Bearer `, `Token `, `Key `,
  `ApiKey `, `Api-Key `, `Bot `, `SSWS `); a header or query parameter whose name carries a
  credential word (`key`, `token`, `secret`, `auth`, `session`, `signature`, `passw`...) never takes
  a literal value; `requires_keys`/`optional_keys` only name keys of the spec's own provider(s)
  (`KeySpec.provider`), never another provider's key (legacy keys without a provider are refused);
  `ignored_status_codes` never refusals/failures/2xx (204 counts as ignored);
  `paginate.max_pages` <= 5 (pages while they produce values when `stop_when_empty`).
* answers: HTTP 202/206, an HTML/XML or JSON page served to a `csv` spec, an (X)HTML root for an
  `xml` spec, truncated, unparsable or > 5 MB answers are ERROR (could not verify), never EMPTY;
  JSON `NaN`/`Infinity`/out-of-range numbers parse as `null`; NDJSON/CSV split lines on LF only;
  `rss` matches roots and items by local name (RSS 1.0 `rdf:RDF`); XML keeps prefixed tag names
  (`dc:date`) and refuses DOCTYPE/entity declarations in the expat handlers (text that only mentions
  them is data); result values are bounded (4096 characters of text, 64 KB of JSON per object) and
  mapping stops at the run deadline or on cancel.
* `results[].format`: `str`, `int`, `float`, `bool`, `lower`, `as_list`, `as_time`; a `tag` result
  becomes one info finding (title `pretty_name`) carrying the tag; a `regex` yields its first group
  (else the match); `match_all` keeps every value.
* `multi_match`: records = values at `path` (a list contributes its items) filtered by `onlyif`;
  results/findings per record, `found`/`absent` on the first page's document.
* presence: `found` / `absent` (rule or `absent_statuses`) / `unknown`; without found/absent rules an
  absence status is EMPTY. A challenge is BLOCKED with the rendered `manual_link` (A9).
* findings: one per rule and run (counts and matched values in `data`), criterion required for
  severity >= low, unique stable titles.
* A5 profile-site specs (accepting `username` or a handle type, or using `{user}` on an `email`: a
  username lookup derived from an address) and A3/A8 unknown-tier/unknown-terms
  specs follow the rules of the README (seeds only, never default, explicit markers, one request,
  a provider whose `http_profile.concurrency` is 1 - one request at a time per site, wave-2 integration,
  POSSIBLE pivots, POSSIBLE tag findings, `high_collision` on handles shorter than 5 characters; a
  redirect is classified, never followed; IOC types only for unknown tiers). A spec receiving
  `person_name` is never default (A3); the reserved tag `offline` is refused.

### Fixtures convention

`tests/fixtures/specs/<name>/` (user specs: `~/.v3lum/specs/<name>/`): `ok.<ext>`,
`error_in_200.<ext>`, `expected.json` (`{"ok": {"status", "attributes" (subset), "pivots" (subset)},
"error_in_200": {"status": blocked|quota|rate_limited|error, "reason_code"}}`), plus the addition
`ok_page<N>.<ext>` for further pages of a paginated spec (pages without one are served empty by
`tests/test_specs.py` and `check_fixtures`). `ok.status` is `ok` or `empty` and equals the spec's
`health_check.expect` (the ok fixture is the answer for the health-check value). Bundled specs are
run over their fixtures by `tests/test_specs.py` in CI; user specs, which no CI runs, are run over
theirs at load by `check_fixtures` (offline, HTTP 200 for both fixtures) and refused when the
outcome differs from `expected.json` (P331 cond 7: the fixtures are the spec's test).

### Health and auto-disable (P331 cond 9)

`load_specs()` reads `health.HealthState.load()` (or `health=`): a spec whose checks failed on 7
consecutive days (`HealthState.consecutive_failed_days`) is compiled **auto-disabled**: it stays
registered and listed (`describe()['spec_disabled']`, `specs.disabled()`), is never default and
refuses ordinary runs with SKIPPED `demoted`, while its `health_check()` carries a `selftest` that
performs the real lookup on the benign value and judges the declared `expect` (HealthResult
ok/blocked/quota/needs_key/dead; an `ok` spec answering without data is `dead`). Cancellation
(`Cancelled`), policy or licence refusals (`PolicyError`, also for a lookup that ends SKIPPED),
`ConfigError` and `OfflineError` propagate to the caller instead of being recorded as a failed day:
**WP25 doctor must catch them** around `selftest(ctx)`. Doctor records the result with
`HealthState.record_check`; the next load after a passing check re-enables the spec.
`HealthState.notices()` carries the doctor notice.

### Tests

`tests/test_specs.py` (bundled specs over their fixtures, the self-test set
`tests/fixtures/specs/_selftest/` loaded as user specs, refusals, ReDoS (structure, cost model, a
catastrophic pattern refused without running it), XML entities and RSS 1.0, error pages served with
HTTP 200, hostile numbers and values, AR12, per-file load isolation, error keys that never disable a
registered module (POL-02), reload, auto-disable and the self-test semantics, the registry contract,
policy/quota equivalence with a hand-written twin, host confinement).
