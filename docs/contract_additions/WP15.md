# Contract additions - WP15 (wave 3)

Evidence store v2, the case audit trail, the hash-chained request ledger and the `cases verify`
engine (P324; A4 BR7, A7 BR13-BR14, A10, AR01/AR03/AR09). Nothing of the frozen guide changes:
`res.raw` is still "saved as sanitized evidence", `res.datasets` / `res.redacted_fields` are still
filled by the engine, `ctx.http` / `ctx.net` keep their documented behaviour, and
`EvidenceStore(case_dir, now=...).save(res, requests=...) -> (path, sha256)` keeps the engine's
entry point. This file adds names and states what module, command and report authors can rely on.

## Details

### What module authors can rely on (no code change needed)

* **Evidence file names carry no value** (A4 BR7): `<module>__<type>__<hmac12>__<sha10>.json`
  (`.json.gz` above 64 KB), `hmac12` = the keyed HMAC of the installation (`hmacid.hmac12`). When the
  installation secret is unavailable the name part is random (fail closed: never a plain hash of the
  value), the record's `entity_hmac` is '' and its `record_key` is `<module>|~<random>`.
* **What is stored**: `res.raw` after the sanitizer (P145) and the central redactor (AR01: configured
  key values and key-like URL parameters masked; raw SECRET_TYPES values of the run's entity and
  pivots written in their persisted form), `res.datasets` citations, `res.redacted_fields`,
  `res.status`, `res.partial` and the request context of every request the run made through
  `ctx.http` / `ctx.net` (method, redacted URL, final URL and redirect chain, status, selected
  response headers when recorded, UA, egress profile, `from_cache`, `fetched_at`). Modules never pass
  request context themselves.
* **fetched_at is never the replay time**: an answer served from the HTTP cache keeps the cache row
  time when the request record carries it (`fetched_at`), else `None` ("unknown"); the record's
  `collected_at` is the runtime clock of the collection. Known gap (open issue for the
  `v3lum/core/http.py` owner): `RequestInfo` does not carry `fetched_at`, `final_url` /
  `redirect_chain` or the response headers yet, so real cache hits are recorded with
  `fetched_at: null` and no `headers`; `request_record` already reads those attributes the moment
  `RequestInfo` (or its `to_dict()`) carries them, with no change here.
* **Redirect chains** are rebuilt from the request log per requesting module and source: a run of
  3xx hops of one module ends at that module's next answer (`final_url`, `redirect_chain`); records
  of other requesters logged in between (the `egress_resolver` DoH lookups that pin each hop, other
  modules) never inherit it.
* A payload nested too deeply to encode raises `ValueError` from `EvidenceStore.save` (the engine
  keeps the result and notes "evidence not saved"), never an exception that stops the scan.
* **Write-once and versions**: a file is never overwritten (0600 in a 0700 case directory, created
  through a hard-linked temporary file; a planted symbolic link or a name with other bytes is
  refused). Collecting the same (module, entity) again in a case writes version N+1 with a diff
  summary (`added` / `removed` top-level field names - keys that look like values are only counted -
  and `changed_leaves`); an unchanged payload is not stored twice.
* **Caps**: settings `evidence_max_file_bytes` (5 MB) and `evidence_max_case_bytes` (200 MB; 0 = no
  cap). A payload that does not fit keeps a prefix of its JSON text and `truncated = {reason, limit,
  original_bytes, original_sha256, kept_chars, note}`; once the case cap is spent only the record of
  the collection (no data) is written. Keep `res.raw` to what an analyst needs as proof.
* **Request ledger** (A7 BR13): every LIGHT/ACTIVE request or connection made through `ctx.http`,
  `ctx.net` (CONNECT records) or the tool runner (EXEC records) is appended to
  `<case_dir>/ledger.jsonl` as it happens, whatever `--no-evidence` says: UTC time, module, method,
  host, resolved IP, port, redacted path (configured secrets, every query value, e-mail-like and
  opaque-token path segments masked), status, bytes, egress profile, opsec. Cache hits and passive
  requests are not ledger lines. A ledger that cannot be written cancels the run (target contact
  stops; fail closed).
* **Policy violations** (P327 cond 5, A8 BR9): a run that ends SKIPPED `policy` because it reached
  for an undeclared host or because a disclosure-`none`/PASSIVE module tried the network writes one
  audit row `policy_violation` `{module, host, violation: undeclared_host|disclosure, reason_code,
  reason, entity_type, disclosure, opsec}`.

### Audit trail - `CaseAudit` (command and core authors)

* Rows are written through `Store.append_audit` (one chain: `hash = sha256(prev_hash +
  canonical_json({case_id, seq, ts, kind, payload}))`, first `prev_hash` 64 zeros, `seq` from 1, `ts`
  UTC) and mirrored byte for byte to `<case_dir>/audit.jsonl` (0600). `case_dir=None` writes the DB
  row only (e.g. the `org-profile` trail of `profile_change` rows). Rows the store wrote itself
  (`cases hold` / `unhold`) are mirrored before the next row.
* Payloads must be metadata only (no bodies, no secrets): every string passes the central redactor.
  `append` raises when the row or its mirror cannot be written (an audit failure is never silent).
* Kinds (`AUDIT_KINDS`): `case_start`, `case_end`, `tlp_change`, `profile_change`, `hold`, `unhold`,
  `policy_violation`, `override` (`cases override` / `cases confirm`, WP18) and `purge` (written by
  the store's purge routine).
* `case_start` payload: started, tool_version, analyst (constructor > setting `analyst` > OS user),
  os_user, purpose, legal_basis, ticket, mode, authorization_ref, scope_sha256, window {start, end},
  egress {profile, ip, checked_at} (+ egress_profile, egress_ip; the IP and its check time come from
  `~/.v3lum/egress_check.json` = `{profile: {ip, checked_at}}` written by `doctor --egress`, WP25),
  tlp, tlp_default, tlp_lowered (`options.tlp_lowered` or `options.tlp_change`, else derived from the
  setting `tlp`), overrides {egress_override, breach_scope: all, show_personal, allow_unknown,
  expand_personal}, org_profile_sha256, licence_profile, targets (seed keys, personal types
  pseudonymised), modules, preset, subject_roles / confirmed_urls_sha256 when set, resumed_from.
* `case_end` payload: ended, duration, counts (findings, correlations, module_runs, status, partial,
  interrupted), tlp, mode, request_count, targets_touched, modules, `requests` = `{ledger_lines,
  ledger_head}` and `evidence` = `{versions, index_head}` (the anchors `verify_case` checks; removing
  lines from the end of a chain is detected against them), policy_violations, the engagement summary
  (refusal targets pseudonymised), since_last_run and notes.
* Retention (A10): on purge the store keeps, for LIGHT/ACTIVE cases and until
  `audit_retention_days`, only the audit rows reduced to `store.ENGAGEMENT_AUDIT_FIELDS` (re-sealed,
  closed by a `purge` row) and `ledger.jsonl` (`store.ENGAGEMENT_AUDIT_FILES`); the mirror and the
  evidence go with the case.

### The engine hook - `AuditHook` (wiring authors: App, shell, watch, batch)

* Install with `AuditHook(store, analyst=...).attach(runtime)` (adds it to `runtime.case_hooks` and
  subscribes to the `http_request` events; idempotent; `detach()` removes both). Installed only as a
  case hook (no `attach`), the ledger is completed at case end from the run logs.
* `on_case_start` fails closed: an audit row or a ledger that cannot be created raises, and the
  engine aborts the scan before any module runs.
* `on_case_end` sets, on the case, `case.meta['engagement']` (LIGHT/ACTIVE cases or cases with
  ledger lines) = `{mode, authorization_ref, scope_sha256, window, egress, egress_override,
  targets_touched {host: count}, request_count, refusals [{target, module, reason_code, reason}],
  ledger {file, lines, head}}` (refusals: coverage rows of LIGHT/ACTIVE modules with reason_code
  `scope`, `hostile_host` or `policy`, at most 200, `refusals_omitted` beyond) and, on a
  re-collection (same case id, or the newest earlier case with the same seed set whose TLP is not
  above this case's), `case.meta['since_last_run']` = `{previous_case, previous_created, new,
  resolved, unchanged, not_rechecked}` (a finding whose module did not answer this time is
  `not_rechecked`, never `resolved`). `case.to_dict()` also carries both at the top level
  (`LIFTED_KEYS`); report and UI authors read them with `engagement_of(case)` /
  `since_last_run_of(case)`. On a re-collection the hook also appends the header line
  `since_last_run_line(...)` to `case.meta['header_notes']`, which the report header renders
  (P324 cond 8; nothing to add in report code).
* After the `case_end` row the hook sets `case.meta['audit'] = {rows, head}` (`STORED_ANCHOR_KEY`):
  the stored case anchors the audit chain, so removing rows from its end (the `case_end` row and its
  ledger/evidence heads included, in the case DB and the mirror alike) is detected. Code that saves
  a case must serialise it after the hooks ran (`case.to_dict()` after `investigate`, as App and
  `cases resume` do). The key is not lifted to the top level of the case dict.

### `cases verify` - `verify_case`

`verify_case(store, case_id, *, case_dir=None) -> VerifyReport` recomputes offline: the evidence
index chain, every evidence file against the index and against the hash in its name, unlisted
files, the `evidence_versions` rows against the index, report hashes (`report_hashes` rows and
`<report>.sha256` sidecars), the audit chain byte for byte (DB rows and their `audit.jsonl` mirror)
and the request ledger chain, against the anchors of the last `case_end` row. A purged case verifies
what is left (the re-sealed minimal audit and the ledger) and says so (`purged=True`). `ok` is True
when `problems` is empty; `warnings` list what could not be checked. `report.lines()` is the CLI
output (first line `PASS <id>: ...` or `FAIL <id>: N problem(s); ...`).

Anchors and the "end of chain" rule: every chain is also checked against heads recorded elsewhere,
because a chain shortened from its end is still well formed. The audit chain is checked against
`case.meta['audit']` of the stored case; the ledger against the `case_end` row's `requests` and the
stored engagement summary's `ledger {lines, head}`; the evidence index against the `case_end` row's
`evidence` (versions indexed later are a warning). A saved case whose last run has a `case_start`
but no `case_end` row is a problem, unless the case notes say the hook could not write it
(`CASE_END_MISSING_NOTE`, a warning) or a later run of an intact anchored case did not finish (a
warning). `evidence_versions` rows are compared with the index on sha256, path, collected_at,
fetched_at and diff_summary.
