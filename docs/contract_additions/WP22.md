# Contract additions - WP22 (wave 4)

Correlation engine v2 (P301): data rules compiled into `correlate.RuleInfo`, per-rule precision
demotion, the P258 natural-person cap for every rule, user rule directories, the homonym-safe
`high_signal_tags` (AR08) and the `v3lum rules` command. Nothing of the frozen guide (contract v2)
is renamed or changes behaviour for modules: `@rule`, `RuleContext`, `RuleInfo`, `run_rules`,
`rules_listing`, `register_compiler` and the graph-fixture harness keep their documented signatures;
everything below is added (keyword-only parameters with defaults, new fields with defaults, new
names).

Who needs it: authors of **batch data rules** (`v3lum/data/rules/<id>.json|toml`), **pack authors**
whose rules concern natural persons (`person=True`), **sanctions / ransomware / leak-tracker module
authors** (the `match_type` convention AR08 reads), **WP25** (doctor: demoted rules and the user
rule directory), **WP19/WP13** (app/engine: the precision table), **WP30** (P258 pack, user rule
ownership checks) and **WP29** (notices: `spiderfoot_correlations`).

## Data rules (`v3lum.rule/1`)

Batch authors may ship a rule as data in `v3lum/data/rules/<rule_id>.json` (or `.toml`; never
YAML in the package) with positive and negative graph fixtures in `tests/fixtures/rules/<rule_id>/`
exactly like a Python rule (section 16; the registry contract test requires them). The full schema
and examples are in [v3lum/data/rules/README.md](../../v3lum/data/rules/README.md). In short:

```json
{"schema": "v3lum.rule/1", "id": "rare_registrar", "version": "1", "code": "", "title": "...",
 "severity": "low", "confidence": "possible", "criterion": "...", "references": ["https://..."],
 "attack": ["T1583.001"], "false_positives": "...", "tags": ["infrastructure"],
 "collections": [{"name": "domains", "entity_types": ["domain"],
                  "filters": [{"field": "attr:registrar", "op": "exists"}]}],
 "aggregation": {"field": "attr:registrar"},
 "analysis": {"method": "outlier", "minimum": 10, "percentile": 10},
 "headline": "{count} domain(s) use the rare registrar {value}",
 "recommendation": "...",
 "suppress": [{"name": "parked", "when": [{"field": "tag:parked", "op": "exists"}],
               "to": "possible", "reason": "parked domains say little about ownership"}]}
```

* fields: `attr:<vocab attribute>`, `tag:<vocab tag>`, `relation:<vocab relation>`, `type`,
  `value`, `finding.source`, `finding.severity` (+ `entity` for aggregation); unknown vocabulary
  names are schema errors;
* operators: `eq`, `in`, `regex` (ReDoS guard), `gte`, `lte`, `exists`, with `negate`;
* methods: `threshold`, `outlier` (with the SpiderFoot noisy-data guard), `first_collection_only`,
  `match_all_to_first_collection` (`match`: exact | contains | subnet), `both_collections`;
* headline placeholders: `{value} {count} {total} {percent} {field} {collection} {entities} {rule}
  {severity}` only;
* only evidence findings count (never `context_only` or `SUP-*`-suppressed), noise nodes are
  skipped (as entities and as `relation:` neighbours, AR06) unless `include_noise`; suppression only downgrades (label, optional lower severity) and
  is recorded as `<rule_id>:<name>` in `suppressed_by` (with `from`/`to` severity labels when it
  lowered the severity);
* evidence: the ids of the findings the finding filters matched and of the evidence findings that
  carry a filtered (or aggregated) tag, then the facts (`attr:registrar=X`, `count=5`, `share=4.0%`);
* `references` are https links that never point at people-search, submission or enumeration
  services (`lint.forbidden_probe`, P327 tables); `tags` never include `RESERVED_TAGS`;
* regexes: see `regex_problems`; subjects are cut to 1024 characters (`MAX_REGEX_INPUT`);
* a rule whose collections select `person_name`/`cpf` (or `natural_person: true`) runs only in a
  case with a recorded purpose and gets the P258 cap.

Schema errors are `RULE_ERRORS` entries (the contract test fails). Data rules and Python rules give
the same `RuleInfo` and `Correlation` shapes (`tests/test_rules_engine.py`).

## Run-time behaviour of `run_rules` (both kinds)

* **why**: a correlation without `why` gets a one-line one (its criterion, else the rule's
  criterion or title). Pack rules that set `why` are unchanged.
* **precision demotion (P301 cond 8)**: with a precision table, a rule whose precision is `< 0.3`
  after `>= 10` votes emits each correlation one severity level lower (INFO stays INFO), adds a
  `suppressed_by` entry `{"rule": "P301-precision", "reason", "from", "to"}` and the tag
  `precision_demoted`. Never disabled. The table comes from, first found: `run_rules(precision=)`,
  `rctx.meta['rule_precision']` (mapping or callable, e.g. `Store.rule_precision`),
  `rctx.meta['store'].rule_precision`, or the store behind `rctx.meta['sightings_lookup']` (the
  App installs `Store.sightings_for` there). Keys are looked up by the correlation's `rule` first,
  then the registered rule id.
* **natural persons (P258 cond 3)**: a CONFIRMED correlation over a `person_name`/`cpf` entity, tagged
  `natural_person`, or from a rule with `person=True` is lowered to PROBABLE
  (`Correlation.downgrade`, label `P258-person-cap`) unless an analyst confirmed it: the tag
  `analyst_confirmed`, its id in `rctx.meta['analyst_confirmed']`, or an evidence finding (by id in
  `Correlation.evidence`) carrying an analyst override labelled `confirmed` with a verdict that is
  not a false positive.

* **read only (P301 cond 5)**: rules taking a context get a `RuleContext` whose `options` (and
  their sets/dicts/lists) and `meta` are copies, so a rule can never change the scan's opsec mode,
  scope, depth or module selection; a rule that changes them, or adds nodes, edges or findings to
  the graph, gets a `RULE_ERRORS` entry (its fixtures then fail in CI). Rules see the same values as
  before; only writes are isolated.

## User rules (`~/.v3lum/rules`, AR12)

`load_rules()` also loads `$V3LUM_HOME/rules` when it exists (never created by V3LUM): nothing loads
unless the directory and every file pass `paths.insecure_reasons()`; each file passes
`lint.lint_data_file` and the schema (JSON, TOML, YAML with the optional extra `yaml`); an id that
is already registered is refused (user rules never replace reviewed or legacy rules). The lint reads
the parsed document (`lint_data_file(path, data=doc)`), so TOML and YAML rules are linted exactly like
JSON ones. Loaded rules
have `RuleInfo.user = True`; every outcome is in `correlate.user_rules_report()` (doctor) and problems
in `RULE_ERRORS` under `user:<file>`.

## AR08: `high_signal_tags` and the `match_type` convention

`high_signal_tags` (still emitting correlations named `tag_<tag>`) reads each tagged evidence finding:

| finding | class | result for `ransomware` / `sanctions` |
|---|---|---|
| `data.match_type` `exact_cnpj`, `cnpj`, `lei`, `wallet`, `domain`, `url` (with or without `exact_`), or the tag sits on a CNPJ / wallet / domain / onion / URL entity | exact | CRITICAL, underlying confidence |
| `data.match_type` `name`, `alias`, `fuzzy`..., tag `name_only_match`, or the tag sits on a person / company / actor / keyword / username entity | name | MEDIUM, POSSIBLE, title `<entity>: possible match - verify identifiers (<tag>)` |
| `data.match_type` `formerly_*` | former | MEDIUM, POSSIBLE |
| on a person / company / actor / keyword / username entity: any other `match_type` that names no identifier (`exact`, `exact_name`, `normalised`, `full`...) | name | MEDIUM, POSSIBLE (an 'exact' name comparison is still a name comparison) |
| anything else (incl. identifier kinds such as `cnpj_root`, `cpf`, `imo`) | unspecified | CRITICAL with >= 2 independent upstream families, else HIGH ('one source - verify') |

Families come from the provider registry (`Finding.source` -> `upstream_family`, narrowed by
`data.upstream_families`) and are counted like CR27 (`independent_families`): a mirror of a family
adds nothing; an aggregator (`Source.embeds`) without a stated upstream counts only when none of the
families it embeds is already counted; findings without a registered source name no family and
count together as one 'unattributed' family only when two different modules (not already counted
through a registered source) report them - so one registered feed plus one unknown feed stays HIGH.
Name-only findings never count toward the two-family path. Module authors of sanctions, ransomware and leak trackers should set
`data['match_type']` and, for name comparisons, the `name_only_match` tag. `takeover` and
`credential_exposure` stay HIGH with the underlying confidence.

## Retired legacy rules

`multi_source_malicious`, `breach_and_infostealer` and `exploitable_exposure` were removed from
`v3lum/correlations/generic.py`; `LEGACY_RULES` now holds `shared_infrastructure`, `seeds_linked`,
`username_reuse`, `young_domain` and `high_signal_tags` (`RETIRED_LEGACY_RULES` lists the three).
The ids `multi_source_malicious` (CR27, WP23) and `exploitable_exposure` (P291 alias, WP23) stay
registered by their packs; `breach_and_infostealer` is replaced by CR09-CR12 (WP24) and is no longer
registered. The frozen guide (section 16) still says "the eight `LEGACY_RULES`": the set is five
since WP22 as the plan mandates (the exemption semantics - only listed v1 ids, superseded by a pack
rule of the same id - are unchanged). Two wave-1/2 tests still assert the old state and need their
owners' update: `tests/test_rule_api.py::test_legacy_flag_on_the_eight_legacy_rules` (WP01) and
`tests/test_engine_suppression.py::test_breach_and_infostealer_respects_generic_and_third_party_addresses`
(WP08; the A4 BR6/BR9-BR10 behaviour it checked now lives in CR09-CR12, `tests/test_pack_breach.py`).
