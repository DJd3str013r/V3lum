## P111 `github_user` - GitHub user enrichment (profile, events, SSH/GPG keys, commit e-mails, activity)

- council: **approved**, priority P1, default_enabled=True, provider_tier=trusted, terms=key-terms, opsec=passive, shares_input=True
- category: username_social; group: G05; inputs: username, url, person_name; produces: email, url, username, domain
- auth: none; key env vars: V3LUM_GITHUB_TOKEN; hosts: api.github.com, github.com, gitlab.com

### Final conditions (binding spec - implement every item)

1. Module username_social/github_user, REST API only: api.github.com/users/{u}, /users/{u}/events/public and /repos/{r}/commits?author= when event payloads lack commits; github.com/{u}.keys, github.com/{u}.gpg and commit .patch as plain-text GETs capped at 1 MB. No parsing of github.com/search or any other HTML (GitHub AUP s.7).
2. person_name inputs go to a separate opt-in module github_user_search (default_enabled False, A3) that uses REST /search/users only; its results are POSSIBLE candidates with expand=False, never auto-expanded.
3. One shared GitHub client and budget for github_user, git_metadata_identity (P115), osv_ghsa (P185) and org_code_footprint (P359): 60 req/h keyless per egress IP, 5,000/h with key 'github', search 10/min; X-RateLimit-Remaining honoured; 403 with rate-limit headers = RATE_LIMITED, never absent; 404 = ABSENT.
4. Key 'github' (exists; V3LUM_GITHUB_TOKEN alias) comes from a team machine account or GitHub App, never an analyst's personal token (rule 1). doctor refuses classic tokens whose X-OAuth-Scopes header is not empty; docs/KEYS.md documents fine-grained tokens as 'public repositories, read-only, no permissions'.
5. Without a token: seeds only, and one coverage line ('GitHub anonymous limit 60/h: add a token with v3lum keys setup') instead of per-entity errors.
6. Commit/event e-mails only for seed accounts. Noreply addresses (^(\d+)\+([A-Za-z0-9-]+)@users\.noreply\.github\.com$) are decoded by one shared helper into an account link and never reported as an e-mail exposure; system addresses are dropped; third-party co-author e-mails are not pivoted.
7. Commit e-mails: relation commit_email, PROBABLE, grouped per address with commit count and first/last date, expand=False unless they match a case entity, never auto-sent to breach modules (A4), kept no longer than retention_days (GitHub AUP s.8 purpose limit).
8. .keys/.gpg are stored as SHA-256 fingerprints and GPG UIDs; GPG UID e-mails follow the commit-e-mail rules. The Ceos activity/stack classifier output is attributes only and never infers sensitive traits.
9. Registry provider github: tier trusted; terms 'key-terms': legal records free_plan_business_use for the GitHub API terms or key_plans.github='business' before corporate use. personal_data_review before default use (A3 BR8).
10. Trimmed fixtures (user, events, keys, gpg, 404, 403 rate limit) are captured from the team network before merge, because the research proxy blocked api.github.com and no path is verified yet; the module enters the default set only after they pass.

Chair rationale: Approved 6-0 at median P1. Every member drops the github.com/search HTML discovery for REST /search/users (GitHub AUP; legal_dpo's floor), and the person_name path is split into an opt-in module because A3 forbids default person_name modules. The architect's and osint_investigator's shared client and budget, redteam_lead's no-scope token check and legal_dpo's machine-account and purpose rules are consolidated. Terms stay 'key-terms' as drafted and apply to every GitHub REST user in this chunk (P115, P185, P359).

Synthesizer conditions (background; the final conditions win on conflict): REST users/{u}, users/{u}/events/public (commit author e-mails; decode NNN+login@users.noreply.github.com), github.com/{u}.keys/.gpg (key fingerprints, GPG UIDs), .patch of public commits; V3LUM_GITHUB_TOKEN optional (60/h anonymous); search-page embedded JSON discovery (Céos) only for person_name inputs and low confidence; activity/stack classifier (Céos) as attributes. GitHub user paths were blocked by the sandbox proxy (unverified) -> re-test from team network.
Notes: Developer identity: e-mails, keys, organisations, linked sites.

## P112 `telegram_public` - Telegram public preview (t.me / t.me/s channel posts)

- council: **approved**, priority P1, default_enabled=True, provider_tier=trusted, terms=open, opsec=passive, shares_input=True
- category: username_social; group: G05; inputs: username, url, keyword; produces: url, domain, btc_address, eth_address
- auth: none; key env vars: -; hosts: t.me
- sources shared with other proposals: {"C0227": ["P357"]}

### Final conditions (binding spec - implement every item)

1. Module username_social/telegram_public: unauthenticated GETs of https://t.me/{name} and https://t.me/s/{name} only. Never an account, session, bot token, Telethon or joining (rule 1). Registry provider telegram: tier trusted, terms open (public web preview); Telegram handles are PERSONAL_TYPES, so personal_data_review comes before default use (A3 BR8).
2. One shared t.me parser (stdlib html.parser, 2 MB page cap) is also used by telegram_channel_watch (P357). t.me/{name} answers HTTP 200 for any handle: FOUND only with the tgme_page_title marker; the generic 'Telegram: Contact @x' page = UNKNOWN 'private or missing: could not read', never ABSENT.
3. Each result is classified as channel, group, user or bot. Personal user profiles yield presence and display name only; posts are read for channels only.
4. Posts come from .tgme_widget_message[data-post] with ?before= pagination: <= 2 pages in the default preset (~40 posts), <= 3 in --preset deep; min_interval >= 2 s on t.me; cache 1 h. Runs on typed handles and on t.me links found in the case.
5. Ingestion scrubbing (P145/AR24) runs before cache, evidence and reports: Luhn-valid 13-19 digit PANs are reduced to BIN6 + last 4, CPF-like numbers masked, third parties' phones and e-mails masked, credentials, combo lines and leaked records dropped. Post HTML is never rendered.
6. Evidence keeps post id, date, URL and an excerpt of <= 300 chars on each side of each matched IOC/brand term (<= 1,000 chars per post); reports quote <= 200 chars of matching posts only; channel dumps are never stored.
7. Post text goes through the core IOC extractor (P172). Only infrastructure IOCs (URL, domain, IP, wallet, onion, Telegram/Discord invite) become pivots: deduplicated, warninglisted (t.me, telegram.org, big platforms), hostile-tagged for P376, defanged, expand=False, shown as one block ('12 URLs, 2 wallets from 40 posts', top 5 each).
8. Forwarded-from channel names become username pivots with expand=False. Media, files, og:image and link previews are never fetched, and links in posts are never visited automatically.
9. Bot tokens and webhook URLs found in posts are SECRET_TYPES: reported as type + SHA-256 prefix, never used (P165 stays rejected), never in clear in evidence or reports.
10. Fixtures: real channel page, user page, generic 'Contact @x' page and a private channel; a test asserts that no media URL is ever requested.

Chair rationale: Approved 6-0 at median P1. All members agree on session-free previews, the tgme_page_title FOUND rule and text-only storage. Where numbers differ the stricter applies: <= 3 pages (architect, osint_investigator) with analyst_ux's 2-page default, cti_lead's 2 s interval, and expand=False for every post-derived IOC (analyst_ux, redteam_lead's hostile tagging). legal_dpo's floor sets the P145 scrubbing before cache and evidence and the presence-only rule for personal profiles.

Synthesizer conditions (background; the final conditions win on conflict): No account/session ever (rule 1); t.me/{name} returns HTTP 200 for any handle -> FOUND only with tgme_page_title marker; channel posts from t.me/s/{name} (.tgme_widget_message[data-post], paginate ?before=), run IOC extraction over post text (urls, domains, wallets, Discord invites, bot tokens); store text only, never media (illegal content risk); cap pages per run.
Notes: High CTI value for ransomware/fraud channels in Brazil.
