## P196 `ransomlook` - RansomLook API

- council: **approved**, priority P1, default_enabled=True, provider_tier=community, terms=open, opsec=passive, shares_input=True
- category: darkweb_ransomware; group: G09; inputs: threat_actor, keyword, company_name, onion; produces: threat_actor, onion
- auth: none; key env vars: -; hosts: ransomlook.io

### Final conditions (binding spec - implement every item)

1. Module darkweb_ransomware/ransomlook. Per-entity lookups via ransomlook.io/api/search?q=<normalised name or domain> (bounded, max_bytes 2 MB), plus a local index synced daily from /api/posts/period/{d1}/{d2} and /api/groups through the dataset manager (offline matching on that path).
2. /api/group/{name}, /api/posts and /api/export (3-163 MB) are never called during a scan.
3. Victim-name normalisation (accents folded; LTDA, S.A., S/A, EIRELI, ME, EPP, Inc and 'Grupo' stripped) and group-alias normalisation are shared core helpers used by P197, P356 and P357; cross-tracker dedupe ('corroborated by N trackers': victim + group alias + date +/- 3 days) is one correlation rule, not code in each module.
4. Matching: an exact domain/website or CNPJ match -> high, critical when the victim is an org_profile entity or a listed supplier, worded 'claimed by <group> on <date> (actor claim, unverified)'; name-only matches -> POSSIBLE 'possible match - verify victim identity', medium at most (e.g. 'Unimed' names hundreds of separate cooperatives).
5. One grouped finding per victim across trackers (P335), counted once in the score. Misses read 'not listed by <trackers> (data as of <date>)', never 'not breached'.
6. Posts are claims stored as metadata and excerpts of <= 300 chars; victims who are natural persons get no description text. Onion and claim URLs are never fetched and screenshots/images never downloaded (they can show leaked documents, rule 3); listed infrastructure is hostile-tagged and defanged.
7. Licence: content CC BY 4.0 with commercial use allowed (ransomlook.io/about, verified 2026-11-26): attribution 'Source: RansomLook (CC BY 4.0)' in every report and export using it; the AGPL service code is not copied. Registry provider ransomlook: tier community, terms open.

Chair rationale: Approved 6-0 at median P1. The licence-clean leak-site tracker for the corporate default. cti_lead, osint_investigator and analyst_ux require domain/CNPJ evidence for severity and POSSIBLE name-only matches; the architect's bounded search plus daily index and the shared normaliser and dedupe rule avoid the 163 MB dumps and duplicated code; legal_dpo's claims wording and redteam_lead's never-fetch rule complete it.

Synthesizer conditions (background; the final conditions win on conflict): Data CC BY 4.0 (commercial OK, attribute); service code AGPL (no code copy); /api/recent, /api/groups, /api/group/{name} can be 3-163 MB (all posts) -> never in the hot path: stream and keep matching posts or use recent; dedupe with ransomware.live by normalised victim + group + date +/- 3 days.
Notes: Independent second leak-site tracker with commercial-friendly licence.

1. Module darkweb_ransomware/ransomware_live. Corporate code path: the PRO API (api-pro.ransomware.live, header X-API-KEY) with one key 'ransomwarelive' (V3LUM_RANSOMWARELIVE_KEY alias; one team token, never several keys). Keyless v2 (api.ransomware.live) runs only in the research profile.
2. Source classes: v2 'noncommercial' (A1), PRO 'license'. Under corporate it needs a company-account PRO key AND that approval in licence_allow: off under the corporate profile until licence-cleared.
3. Until it is cleared, RansomLook (P196) and ransomfeed (P356) are the corporate defaults. Without a key or licence: one coverage line plus the manual ransomware.live victim-search link.
4. searchvictims/{name} by normalised company name and by domain through the shared normaliser (P196); recentvictims through the dataset manager for watch; the same victim matching, grouping and 'not listed' wording as P196; dedupe through the shared ransomware correlation rule.

6. claim_url onions and screenshot URLs are never fetched or embedded (screenshots can show leaked documents) and are shown as links with a warning. Ransom-note contacts (onions, qTox, e-mail) and group IOCs become hostile-tagged pivots with expand=False. The PRO key is redacted everywhere (AR01).
7. PRO success fixtures are captured with the team key (only v2 fixtures exist). Registry provider ransomware_live: tier community.

Chair rationale: Approved 6-0 at median P1 (cti_lead and legal_dpo voted P2). cti_lead and legal_dpo verified that the free PRO key alone does not clear corporate use (written approval required), which is stricter than A1 BR15's 'key-terms' for PRO and is adopted as the legal floor; the module is a default candidate that stays off under the corporate profile until licence-cleared (A3 BR4). The architect's single PRO code path and fixtures, osint_investigator's screenshot rule and redteam_lead's hostile tagging are kept.

Synthesizer conditions (background; the final conditions win on conflict): searchvictims/{name} and recentvictims; search by company name AND domain with legal suffixes normalised (LTDA, S.A., Inc); the free API is 'not intended for corporate or business use' -> corporate deployment needs API PRO (V3LUM_RANSOMWARELIVE_KEY, also unlocks IOCs/notes/YARA) or rely on RansomLook (CC BY 4.0); never open claim_url onions automatically; victim_of relation + ransomware tag (critical when the org or a supplier is listed). ### Final conditions (binding spec - implement every item)

1. Two modules split by disclosure. crypto_sanctions_offline (disclosure none, TLP:RED-safe): the 0xB10C OFAC sanctioned-address lists (MIT lists over US public-domain OFAC data) via the dataset manager, daily, per chain; matching EVM lowercase, base58 exact, bech32 lowercase; list date/commit kept per match.
2. crypto_sanctions_onchain (disclosure third_party): the Chainalysis sanctions oracle eth_call isSanctioned(address) (selector 0xdf592f7d), USDT isBlackListed (0xe47d6060) and USDC isBlacklisted (0xfe575a87) on a configurable eth_rpc setting (default PublicNode), plus TronGrid triggerconstantcontract on the USDT-TRC20 contract, all in the first build.
3. One EVM JSON-RPC helper shared with evm_explorers (P212) and the TronGrid client shared with tron_explorer (P207); ABI encoding unit-tested; per-chain oracle/contract addresses kept in data with their source; checksums through the P217 pure-Python Keccak.
4. A result other than 0x..00/0x..01, a JSON-RPC error or a timeout -> ERROR (could not verify), never 'not sanctioned'. Chainalysis REST (key 'chainalysis') is a second check covering non-EVM chains; its 403 HTML 'IP not on the Chainalysis Allowed IPs List' -> BLOCKED/NEEDS_KEY.
5. Labels: an OFAC list or Chainalysis oracle/REST hit -> tag sanctions, critical: 'address on the OFAC SDN list (US)' citing SDN entity, programme and list date, with 'stop transactions and escalate to compliance'; a USDT/USDC issuer blacklist hit -> tag issuer_freeze, high, 'frozen by issuer (Tether/Circle)', never 'sanctioned'.
6. A list match is not a legal determination: escalate to compliance/legal and take no automated adverse action against natural persons (LGPD art. 20). Stale lists are flagged; misses read 'not on OFAC lists as of <date>', never 'not sanctioned' (rule 5). GoPlus 'sanctioned' flags are not authoritative: the sanctions tag comes only from this module.
7. Terms: OFAC lists 'open'; oracle and stablecoin calls 'open' (public contracts, RPC provider ToS recorded); TronGrid and Chainalysis REST 'key-terms' (company accounts, plans recorded). Registry tiers: Chainalysis, PublicNode (Allnodes) and TronGrid (TRON DAO) trusted.

Chair rationale: Approved 6-0 at median P1. The architect's floor splits offline lists and RPC calls so the offline part stays TLP:RED-safe and RPC errors never read as 'not sanctioned'; osint_investigator puts the TRON USDT freeze check in the first build; cti_lead, legal_dpo and analyst_ux separate sanctions from issuer freezes and forbid automated adverse action.
