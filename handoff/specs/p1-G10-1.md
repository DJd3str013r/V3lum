- council: **approved**, priority P1, default_enabled=True, provider_tier=trusted, terms=open, opsec=passive, shares_input=False

### Final conditions (binding spec - implement every item)

1. Sources: OFAC SDN CSV from the Sanctions List Service (US government work, public domain), UN consolidated XML (UN public information) and EU FSF CSV (EU open data, reuse with attribution; the Commission's public token is a config value). Legal floor: api/data.opensanctions.org are removed from this module (CC BY-NC data belongs to P222 only).
2. Providers (dataset downloads, no value sent): OFAC/US Treasury, UN Security Council and the European Commission, all trusted tier.
3. Datasets only through the dataset manager (`v3lum data update sanctions`; TTL 24 h for OFAC and UN, 3 days for EU FSF ~25.5 MB), each validated (format and minimum rows) before replacing the previous copy, with source date, fetched_at and sha256 recorded. Scans never download them (A6: > 5 MB).
4. Matching is local (disclosure 'none', allowed at TLP:RED). A missing list gives UNAVAILABLE reason_code 'dataset' ('run v3lum data update sanctions'); a list fetched more than 7 days ago gives 'could not screen against <list> (dated <date>)' in coverage. Neither case ever reads 'no match'.
5. Parsing: UN XML through the core safe XML helper, built with this P1 item if absent and shared by every XML parser (DOCTYPE and entity declarations rejected, size caps); EU FSF is ';'-separated with a BOM; OFAC 'Digital Currency Address' remarks are indexed per chain.
6. One shared matcher, core/namematch.py: NFKD accent strip, casefold, legal-suffix removal (LTDA, S.A., EIRELI, ME, EPP, LLC, LTD...), a token blocking index built once per list version, deterministic token-set Jaro-Winkler in pure Python (rapidfuzz only as an optional accelerator with identical scores, both paths tested). P240, P244, P254 and P221 reuse it.
7. Wallets: exact match of normalised addresses (base58/bech32 as-is, EVM and TRON normalised) against OFAC remarks gives a CRITICAL 'sanctioned wallet' finding, confidence CONFIRMED, with programme (e.g. CYBER2, DPRK3), SDN uid and list date. 'Sanctioned' is used only for exact identifier matches (wallet, IMO, registration number, CNPJ).
8. Names: score >= 0.90 (named constant) gives 'possible match - confirm identity', confidence POSSIBLE (<= 0.6), severity at most MEDIUM unless a second identifier also matches (DOB, nationality, document, address, wallet, IMO); never CRITICAL.
9. Person hits are lowered by the P252 homonym score and common-name hits stay INFO. At most 5 candidates per list, each with list, programme, listing date, matched alias and score.
10. Legal floor: person names are screened only for subjects the analyst entered in a due-diligence case with a recorded purpose, or QSA partners of a CNPJ under that due diligence when the analyst enables the due-diligence option; never names from pivots or free text (reason_code 'privacy' otherwise). No 'sanctioned' verdict on a natural person without analyst confirmation.
11. threat_actor inputs resolve through the P295 alias index and match SDN/UN names: a designated actor's card shows 'OFAC/UN designated (<date>) - payments may be prohibited, escalate to legal'. Company names of the case's companies and wallets from any source are screened.
12. Only matched entries are kept in the case (A10). The previous list version is kept so delistings show as 'formerly listed (<date>)'. Reports carry the UN/EU attribution line and each list's publication date.
13. Performance and tests: < 300 ms per name on a synthetic 50k-alias list (benchmark test). Fixtures: an SDN row with a digital-currency remark, an EU FSF row (';' + BOM), a UN XML entry, a common-name non-match; tests for the wallet exact hit, fuzzy hit, homonym downgrade and stale-list message.

Chair rationale: Approved 6-0 at median P1 (redteam_lead voted P2). Offline screening discloses nothing and answers the ransomware-payment question for OFAC wallets. legal_dpo's floor removes the CC BY-NC OpenSanctions hosts and purpose-gates person names with no 'sanctioned' label on people. The architect's floor: dataset manager only, never 'no match' on a missing or stale list, a safe XML parser and one shared pure-Python matcher with a benchmark. Severity follows analyst_ux and the architect (CRITICAL only for exact wallet matches, consistent with AR08), and cti_lead's second-identifier cap, osint_investigator's scope and the delisting history are kept. It stays default-on as an offline module (A3), with person-name screening gated by purpose.

Synthesizer conditions (background; the final conditions win on conflict): Daily downloads matched locally with fuzzy name matching (presented as potential matches with score): OFAC SDN CSV via Sanctions List Service (remarks include 'Digital Currency Address' -> crypto matches), UN consolidated XML, EU FSF CSV (public token dG9rZW4tMjAxNw in the URL); OpenSanctions data is excluded here (CC BY-NC, see opensanctions).
Notes: Core sanctions screening without sending names anywhere.

### Final conditions (binding spec - implement every item)

1. Offline module: disclosure 'none' (no network at all; ScopedHttp refuses any request), terms 'open', provider tier 'n/a'; allowed at TLP:RED. Pure-stdlib extension of core/validators.py.
2. Alphanumeric CNPJ (IN RFB 2.229/2024, issued from July 2026): regex ^[0-9A-Z]{12}[0-9]{2}$ (DVs stay numeric), char value ord(c)-48, weights 5,4,3,2,9,8,7,6,5,4,3,2 then 6,5,4,3,2,9,8,7,6,5,4,3,2, r = sum % 11, DV = 0 if r < 2 else 11 - r; HQ CNPJ derived from the 8-digit root. Vectors: 12.ABC.345/01DE-35, 00.000.000/0001-91 and invalid-DV cases.
3. CPF (rule 4 floor): validated offline only (mod 11, weights 10..2 and 11..2, repeated digits rejected); never a lookup key online or against datasets, never generated, enumerated or completed from masked forms. A unit test asserts that a text with a valid CPF makes zero HTTP requests.
4. The CPF fiscal-region digit is an info-only cross-check worded 'CPF issued in fiscal region N (UFs)', never residence. Wording everywhere separates 'check digits valid (format only)' from existence or registration.
5. Masking (AR24): one core masking function, with tests, masks CPF as ***.456.789-** in display_value, terminal, HTML/MD/JSON/STIX, evidence filenames, logs, --debug and the case-DB index; CPFs are never pivoted. --show-personal unmasks a single view and is recorded in the case audit.
6. PIS/NIS, titulo de eleitor, RENAVAM, CNS and CNH get validators and masking only: they are never auto-detected entity types (several are 11 digits and collide with CPF and phones), never pivots, and the P327 lint rejects any module accepting them as lookup keys. Their validators ship only with official test vectors.
7. Typing gate: an 11-digit string is typed CPF only with valid check digits AND context (CPF label, the ###.###.###-## mask or a form field); in phone context (DDD prefix, tel/whats/zap words, wa.me) it is a phone. A fixture of valid-DV phone numbers must not become CPFs.
8. The BR entity extractor is a rule set inside the shared P172 extraction engine, not a second extractor: regex candidates, then checksum gating, priority BR Code > boleto (47/48) > CNJ (20 digits, mod 97) > CNPJ > CPF > phone, each entity with provenance and a type confidence. Tests on BR scam-message fixtures.
9. Plates: validation and old<->Mercosul conversion only, with test vectors (both forms usable for text search); no owner lookups. CEP format and PIX key types (CPF, CNPJ, phone, e-mail, EVP) are validated offline.
10. Tests: the 18 research vectors plus the RFB alphanumeric example, the phone/CPF collision fixture and the masking tests in every renderer.

Chair rationale: Approved 6-0 at median P1: every Brazilian flow starts here and the alphanumeric CNPJ is already issued. legal_dpo's rule 4 floor (CPF never a lookup key, universal masking, other identifiers masked and never pivoted, no CPF generation) and the architect's floor (stdlib, one masking function, no auto-detected 11-digit types, the extractor inside P172) are adopted. cti_lead and osint_investigator supplied the phone/CPF typing gate, analyst_ux the format-only wording. ## P233 `boleto_pix` - Boleto and PIX BR Code parsers + bank tables (BCB STR participants, BrasilAPI banks/PIX participants)

- council: **approved**, priority P1, default_enabled=True, provider_tier=community, terms=open, opsec=passive, shares_input=False
- category: brazil_public_data; group: G10; inputs: boleto, pix_key, text_blob, file; produces: url, domain, company_name
- auth: none; key env vars: -; hosts: bcb.gov.br, brasilapi.com.br

### Final conditions (binding spec - implement every item)

1. Offline pure-Python parsers. Boleto bancario (47): linha digitavel -> barcode bank(3)+currency(1)+K+factor(4)+value(10)+free(25); field DVs mod 10, general DV mod 11 (weights 2..9; 0/10/11 -> 1). Arrecadacao (48): mod 10 when the 3rd digit is 6/7, the mod-11 variant (r 0/1 -> 0, r 10 -> 1) when 8/9; segment decoded.
2. Due date: the factor wrapped on 2025-02-22 (9999 = 2025-02-21, new 1000 = 2025-02-22); compute both cycles, choose the date nearest to today and flag ambiguity, showing both dates when ambiguous.
3. PIX BR Code: EMV TLV parser bounded (payload <= 512 bytes, nesting depth 2), merchant account template 26-51 with br.gov.bcb.pix, CRC16/CCITT-FALSE (poly 0x1021, init 0xFFFF) over the payload through '6304', checked against the BCB manual vector (1D3D). Extract merchant name/city, key type, key, txid and amount; a bad CRC reads 'altered or corrupted payload'.
4. Keys (legal floor): CPF keys are masked and never pivoted (rule 4); e-mail and phone keys become entities (relation pix_key_of) with expand=False and trigger no automatic breach, stealer, username or phone-reputation lookup, only analyst-initiated ones; CNPJ keys pivot to the P236 chain (who receives the money); merchant names of natural persons are not pivoted to person modules.
5. Legal floor: the dynamic BR Code location URL is never fetched in any mode (fetching is a payer-side action that returns payee personal data); only its host becomes a defanged domain pivot with expand=False; the full location URL stays a masked attribute, never a url entity. No DICT lookups (no lawful public DICT access for third parties).
6. Verdicts: barcode bank differing from the bank named in the document or OCR text is HIGH 'boleto bank mismatch: possible tampering' (PROBABLE); a PIX merchant name or key CNPJ root that does not match the claimed brand (org_profile brands, P360, P236) is MEDIUM 'payee differs from claimed brand'. Neither is ever labelled malicious on its own.
7. Check-digit or CRC failure reads 'invalid or altered code (typed or altered line)'; when the input came from OCR (P363) or a QR decode (P261) it reads 'could not verify (OCR)' instead.
8. Plain-language verdict line first (e.g. 'Boleto: check digits OK - bank 341 (Itau), due 2026-12-01, R$ 1.234,56' or 'CHECK DIGIT MISMATCH: altered or mistyped'); PIX shows merchant, city, key type (masked key), txid, amount and CRC status.
9. Bank, ISPB and PIX-participant tables are full-list datasets (BCB STR CSV with UTF-8 BOM and ',' separator; BrasilAPI banks and PIX participants), refreshed weekly by the dataset manager with a bundled BCB snapshot so triage works offline; never per-value API calls (disclosure 'none'). Each table shows its refresh date. Tiers: BCB trusted, BrasilAPI community.
10. Fixtures: the BCB manual vector, a tampered boleto and BR Code, both due-date cycles, and the STR/BrasilAPI lists re-captured untruncated (the research samples are truncated).

Chair rationale: Approved 6-0 at median P1 (redteam_lead voted P2): boleto and PIX tampering is a top Brazilian fraud pattern. legal_dpo's floor sets key handling (CPF masked, e-mail/phone keys without automatic fan-out) and forbids fetching the dynamic payload URL, so osint_investigator's optional LIGHT fetch is not adopted (redteam_lead and the architect also wanted no automatic fetch). The architect's floor: offline parsers with bounds and vectors, full-list tables through the dataset manager plus a snapshot, no per-value API calls. Severities: osint_investigator's HIGH for a boleto bank mismatch, labelled as possible tampering, and cti_lead's MEDIUM payee mismatch with no 'malicious' label. Tier community is the lowest of the dataset providers (BrasilAPI); terms open. Audit: the payload URL yields a domain pivot only, as legal_dpo's condition requires.

Synthesizer conditions (background; the final conditions win on conflict): Offline parsers: boleto bancario (47) / arrecadacao (48) with DV checks, bank code from barcode vs claimed issuer, due-date factor reset at 1000 on 2025-02-22; PIX BR Code (EMV TLV, CRC16 validated with the BCB manual vector 1D3D) -> merchant name/city, key type, dynamic payload URL -> domain pivot; bank/ISPB tables from BCB STR CSV (UTF-8 BOM, ',') and BrasilAPI banks/PIX participants cached 7 d (sample files are truncated: refetch for fixtures).
Notes: Detects tampered boletos/QR codes pasted by fraud victims.
