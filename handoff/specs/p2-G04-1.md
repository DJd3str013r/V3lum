## P086 `github_email_pivot` - E-mail -> GitHub (commit author search, user search in:email)

- council: **approved**, priority P2, default_enabled=True, provider_tier=trusted, terms=key-terms, opsec=passive, shares_input=True
- category: email; group: G04; inputs: email; produces: username, url
- auth: none; key env vars: V3LUM_GITHUB_TOKEN; hosts: api.github.com

### Final conditions (binding spec - implement every item)

1. Endpoints: search/commits?q=author-email:{email} (sorted by date) for logins and repositories, and search/users?q={email} in:email for public profile e-mails.
2. Team-owned token only (rule 1): key 'github' (already in config.KNOWN_KEYS) in the Authorization header; legal records the token's plan as business-compatible (A1). Search limits (10/min unauthenticated, 30/min with token) via min_interval; 403/429 secondary limits give RATE_LIMITED ('could not verify'), with the token hint once.
3. Runs on analyst-typed seed addresses for third parties and on org_profile domain addresses; never on addresses found as pivots or in pasted text unless the analyst selects them. As a provider receiving PERSONAL_TYPES it enters the default set only after personal_data_review is recorded (A3 BR8); a case purpose is recorded (AR16).
4. A login is reported only after an exact e-mail match in commit metadata or the public profile; fuzzy user-search hits are discarded (13 hits for test@example.com).
5. Confidence: commit author e-mails are self-asserted, so commit-only matches are POSSIBLE (<= 0.4); a signature-verified commit or an address public on the profile gives PROBABLE (<= 0.6); never CONFIRMED.
6. Placeholder and role addresses (noreply, test, admin, octocat@github.com) are ignored or down-weighted and deduplicated by author.login. noreply addresses (<id>+<login>@users.noreply.github.com) are decoded to the user id.
7. Minimisation: keep login, profile URL and the matching repository/commit references only (no bio, location or follower harvesting). Username pivots are expand=False and never auto-expand into further people lookups.
8. Purpose limitation (GitHub AUP s.7, LGPD): security investigations inside a case only, never profiling, HR/performance use, marketing or resale; employees' addresses only under the company security policy and privacy notice; the processing is listed in the ROPA (docs/LEGAL.md).
9. Fixtures are re-captured from the team network (api.github.com was blocked in the research sandbox); the recorded search fixtures cover parsing and the fuzzy-match discard.

Chair rationale: Approved 6-0 at median P2. legal_dpo's floor: a team token, exact matches, minimal fields, no auto-expansion, the AUP purpose limit and the ROPA entry. cti_lead: commit e-mails are self-asserted (POSSIBLE unless verified). osint_investigator and cti_lead: seeds and own-domain addresses only, placeholders ignored. The architect and analyst_ux: header token, rate-limit mapping, exact-match confirmation, expand=False usernames. GitHub: tier trusted; key-terms via the team token.

Synthesizer conditions (background; the final conditions win on conflict): search/commits?q=author-email:{email} (sort by date) -> logins + repos; search/users?q={email} in:email; unauthenticated search limit 10/min, with V3LUM_GITHUB_TOKEN 30/min; the sandbox proxy blocked GitHub user paths (re-test from team network); commit e-mail <-> login links are PROBABLE identity links (noreply ids decoded).
Notes: Strong e-mail -> developer identity pivot (commit metadata).

## P087 `gravatar` - Gravatar profile (REST v3 by e-mail hash) + avatar existence

- council: **approved**, priority P2, default_enabled=True, provider_tier=trusted, terms=open, opsec=passive, shares_input=True
- category: email; group: G04; inputs: email, username; produces: username, url, domain
- auth: none; key env vars: V3LUM_GRAVATAR_KEY; hosts: gravatar.com, api.gravatar.com, en.gravatar.com

### Final conditions (binding spec - implement every item)

1. Hash locally and never send the plaintext address: SHA-256 of the trimmed lowercase e-mail for GET api.gravatar.com/v3/profiles/{hash}; MD5 only for legacy avatar URLs. Hash lookups are still a disclosure (e-mail hashes are dictionary-reversible personal data), so the TLP and privacy gates apply.
2. Runs on analyst-typed seed addresses for third parties and on org_profile domain addresses; it enters the default set only after personal_data_review is recorded for Gravatar (A3 BR8).
3. Unauthenticated limit 100/h from X-RateLimit headers (optional key 'gravatar' raises it); 429 gives RATE_LIMITED. A 404 {'error':'Profile not found'} is a declared absence ('no public Gravatar profile'). Avatar existence via d=404.
4. Keep only the display name, verified-account URLs and the avatar hash. verified_accounts become username/url pivots as PROBABLE identity links (expand=False); free-text profile links are POSSIBLE.
5. Avatar images are never loaded into reports (self-contained reports, P336); they stay links. Avatar correlation uses file or perceptual hashes only, never face recognition or face embeddings (no biometrics, LGPD art. 11).
6. Tests with the recorded v3 404 and schema fixtures.

Chair rationale: Approved 6-0 at median P2 (architect voted P1). legal_dpo's floor: local hashing, only display name, verified accounts and avatar hash kept (osint_investigator's location and about text are not adopted), no biometric processing. cti_lead and osint_investigator: seeds and own-domain addresses only and the PROBABLE/POSSIBLE split. The architect: 429 mapping and avatars as links only. Gravatar (Automattic): tier trusted, terms open.

Synthesizer conditions (background; the final conditions win on conflict): Hash locally (SHA-256 of trimmed lowercase e-mail for v3; MD5 only for legacy avatar URLs), never send the plaintext address; GET api.gravatar.com/v3/profiles/{hash} (unauthenticated limit 100/h via X-RateLimit headers; optional V3LUM_GRAVATAR_KEY), avatar existence with d=404. verified_accounts -> username/url pivots marked PROBABLE identity links; store avatar hash for avatar_correlation; do not load avatar images into reports (external resources).
Notes: Turns an e-mail into linked public profiles with verified accounts (strong identity link).
