## P107 `profile_id_extractor` - Profile ID/metadata extraction from found pages (socid_extractor schemes)

- council: **approved**, priority P2, default_enabled=True, provider_tier=n/a, terms=open, opsec=passive, shares_input=False
- category: username_social; group: G05; inputs: url, username; produces: username, email, url
- auth: none; key env vars: -; hosts: -

### Final conditions (binding spec - implement every item)

1. Not a separate fetching module: a shared helper core/profile_ids.py wrapping socid-extractor (MIT, pinned to a tested version, optional extra, attribution in THIRD_PARTY_NOTICES) that username_check (P113) and the profile enrichers call on response bodies they already hold. It makes no request, so the caller's disclosure and TLP status are unchanged.
2. Only parsing functions are called, never helpers that fetch; bodies are capped at 2 MB before regex schemes run in memory; nothing is fetched from extracted URLs.
3. Extracted stable ids (uid), created_at and similar fields become attributes of that profile. Extracted usernames are filtered by the plausible-username check (maigret is_plausible_username logic, MIT).
4. Extracted identifiers are listed under 'linked accounts found on profile' with the source page and become pivots with expand=False in the default preset. Recursion depth <= 1, only from PROBABLE+ links, only in --preset deep or on analyst selection, at most 2 auto-expanded handles per seed.
5. A platform-qualified account the owner linked may be enriched by that platform's own enricher (one request each); bare usernames never go to the username_check pack without analyst confirmation.
6. Real names, e-mails and phones extracted stay attributes of that profile (POSSIBLE), pivots with expand=False, never auto-pivoted into person_name modules (A3) and never auto-sent to breach/stealer modules (A4).
7. Extracted links and handles are owner-written (attacker-controlled when the subject is an actor): passive modules only, never LIGHT/ACTIVE. Tests: one trimmed saved-page fixture per enabled scheme (none exist today).

Chair rationale: Approved 6-0 at median P2 (osint_investigator voted P1). The architect's floor turns it into a helper inside the fetching modules, because the module API cannot share another module's responses, and sets recursion depth <= 1 (stricter than the depth 2 asked by osint_investigator and analyst_ux, whose 'deep or analyst selection only' and 2-handle cap are kept). legal_dpo's no-auto-expansion of names and contacts and redteam_lead's passive-only rule are included. As a no-network helper: tier 'n/a', terms 'open' (A1 BR20).

Synthesizer conditions (background; the final conditions win on conflict): Run socid_extractor (MIT, pip socid-extractor, Python >= 3.10) schemes over pages already fetched by username_check/enrichers (no extra requests); extracted usernames filtered by maigret is_plausible_username; recurse depth <= 2 only for PROBABLE+ links.
Notes: Stable numeric IDs, real names and linked accounts from profile pages.

## P114 `avatar_correlation` - Avatar correlation (dHash) + Gravatar/unavatar avatar hashes

- council: **approved**, priority P2, default_enabled=True, provider_tier=community, terms=open, opsec=passive, shares_input=True
- category: username_social; group: G05; inputs: url, username, email; produces: 
- auth: mixed; key env vars: V3LUM_UNAVATAR_KEY; hosts: unavatar.io

### Final conditions (binding spec - implement every item)

1. Module username_social/avatar_correlation runs only when >= 2 FOUND profiles in the case have avatars; <= 30 avatar downloads per case and one download per avatar URL per case.
2. Avatars are fetched only from http(s) URLs on an allow-list of avatar/CDN hosts of trusted or community platforms in the username pack (e.g. avatars.githubusercontent.com, secure.gravatar.com, cdn.bsky.app, pbs.twimg.com) through the core SSRF guard; redirects only within the allow-list; avatars on other hosts (self-hosted, personal or target domains) are skipped.
3. Pillow as an optional extra with a pinned patched minimum version; dHash on Pillow alone (no imagehash/numpy/scipy). max_bytes 512 KB; Image.open restricted to JPEG/PNG/GIF/WEBP (SVG never parsed); MAX_IMAGE_PIXELS 16M with DecompressionBombError caught; first frame only.
4. No face detection, cropping, facial recognition or reverse face search (biometric data, LGPD art. 11): whole-image dHash only, with a test asserting that no face/biometric library is imported. Avatars are processed in memory and discarded; only URL, SHA-256 and dHash are stored; images are never uploaded to reverse-image services.
5. Matching: Hamming distance <= 8 = 'same avatar image (dHash distance N)', PROBABLE at most and only together with another identity signal, never 'same person' and never CONFIRMED on its own. Flat/default avatars (grayscale stddev < 6) and a bundled per-platform default/placeholder hash list are ignored.
6. Common images are not identity signals: an image equal to an org_profile brand logo is reported as 'uses <brand> logo' (impersonation signal), and an image seen on > 3 unrelated accounts in the case or in sightings is recorded only as 'same image'.
7. Gravatar: hash(normalised e-mail) (SHA-256 and legacy MD5) is computed locally and compared with avatar URLs already found; this module never queries Gravatar with a case e-mail's hash (profile lookups by hash belong to gravatar, P087, under its own TLP and privacy gates); only avatar URLs found on profiles are fetched (such a URL already carries its owner's hash).
8. unavatar.io is not in this build: unknown tier (A8) with unreviewed terms; it may be added only after legal records its terms and tier, never default-enabled, never at TLP:AMBER+ and never sent personal identifiers while unknown.
9. Reports show each matched pair (profile URLs, dHash distance) as text without thumbnails: only URL, SHA-256 and dHash may be stored (legal floor) and reports load nothing external (P336). Tests use synthetic image fixtures.

Chair rationale: Approved 6-0 at median P2. legal_dpo's floor (no biometrics, store only URL/SHA-256/dHash, unavatar.io gated as unknown tier) and the architect's floor (SSRF guard, host allow-list, decompression limits, patched Pillow) shape the spec; redteam_lead's CDN-only fetching avoids tracking-pixel exposure. analyst_ux's 64 px thumbnails are not adopted because they would store image content against legal_dpo's floor; the brand-logo and common-image exclusions come from cti_lead, osint_investigator and analyst_ux. unavatar.io is held out of the build so the module keeps a community-tier provider set.

Synthesizer conditions (background; the final conditions win on conflict): Download each found avatar once (max 512 KB, Pillow MAX_IMAGE_PIXELS), compute dHash; Hamming <= 8 between accounts = PROBABLE link, ignoring flat/default avatars (grayscale stddev < 6); avatar MD5/SHA-256 == hash(email) = PROBABLE; unavatar.io only with key (V3LUM_UNAVATAR_KEY). No facial recognition (biometric data).
Notes: Strong cross-platform identity signal (CR34).

- auth: none; key env vars: -; hosts: raw.githubusercontent.com, threatactorusernames.com

### Final conditions (binding spec - implement every item)

1. Offline module cti_framework/threat_actor_handles (disclosure none): the spmedia Threat-Actor-Usernames-Scrape dataset (MIT) through the dataset manager (weekly), indexed at refresh into SQLite (lower-cased handle -> forum, list date), never a 1.1M-entry in-memory set; default_enabled False (opt-in per scan).
2. The threatactorusernames.com API is not in this build: an unknown-tier operator with no terms (2026-11-26), and A8 forbids sending usernames to unknown-tier providers. It may be added later as a separate opt-in module (disclosure third_party) only after legal records terms and a tier of community or higher.
3. Exact, case-folded match only. Handles shorter than 5 chars, purely numeric or in a bundled common-username/first-name list are skipped; dictionary words are labelled 'common handle: low signal'.
4. A hit is info/low: 'a user with the same handle appears on forum lists: X, Y (scrape date)', confidence POSSIBLE (<= 0.3), 'handle collision likely' (benign 'octocat' matched two carding forums); never auto-expanded, never counted in CR27, never raises the score alone or creates an identity link.
5. Runs only on analyst-typed usernames and threat_actor entities, never on identifiers whose provenance is an org_profile identity (local part of an own-domain e-mail, org public-members lists) except in an insider case with a recorded purpose (test with such a provenance chain).
6. Reports show only the matched handle, forum names and list date; the dataset is never exported or redistributed. A trimmed dataset fixture is captured before merge (only API fixtures exist).

Chair rationale: Approved 6-0 at median P2. Every member makes the offline dataset the default path and keeps the signal weak because of handle collisions. legal_dpo's floor bars sending usernames to the unknown-tier API, so the API adapter waits for a legal review instead of shipping as an opt-in that A8 could never allow. The architect's on-disk index, redteam_lead's employee-provenance exclusion and analyst_ux's default-off wording are kept. Offline: tier 'n/a', terms 'open'.

Synthesizer conditions (background; the final conditions win on conflict): Prefer the offline spmedia Threat-Actor-Usernames-Scrape dataset (MIT, ~1.1M handles across 30 forums) matched locally; threatactorusernames.com API only on request (the query leaks the handle). Exact match only; always a WEAK indicator (benign 'octocat' hits two carding forums); never profile employees with it.
Notes: Flags handles also seen on criminal forums.

### Final conditions (binding spec - implement every item)

1. Module company_org/org_code_footprint reuses the shared GitHub (P111), GitLab, Codeberg, npm, PyPI and Docker Hub clients (one budget per provider): company name/domain -> candidate orgs (GitHub search type:org, GitLab groups?top_level_only=true, Codeberg orgs, npm '@scope/' + maintainer:, the PyPI organisation page, Docker Hub /v2/orgs/{org}).
2. An org counts as confirmed only on a verified domain/blog match with org_profile or analyst confirmation (name collisions). Unconfirmed orgs are listed as candidates without expansion and yield no secret findings or member pivots.
3. In the default set it runs only for org_profile-confirmed orgs (the own organisation); suppliers and other companies only as explicit seeds with a recorded purpose (-M and --purpose).
4. Default preset: a fast inventory (API only, <= 15 s, Module.max_requests <= 10 per entity) with repo/member counts and the 5 most recent repos per confirmed org (repos <= 30, recent first; forks skipped unless the org committed to them). Public members: count only, usernames on demand as expand=False pivots; members' personal profiles are not enriched without a case reason.
5. Deep preset or -M only: secret scanning (secret_scanner rules, P312) of the current tree from the provider's archive download (codeload/GitLab/Codeberg tar.gz) streamed through the core safe-archive helper in memory: no git binary, no extraction to disk, nothing built or executed, repo skipped when the API size is > 50 MB, 1 MB per member, binaries skipped; its own time budget and a progress line.
6. Secrets: type, file, commit, line and a keyed fingerprint with at most the first 4 characters; full values never reach evidence, cache, case DB, reports or logs and are never tested, validated or used (rule 1; Codigo Penal art. 154-A); worded 'exposed in public history; validity not tested'; one grouped finding per repo, high only for org-confirmed repos.
7. Third-party secrets (suppliers, customers) go to a disclosure workflow, not into shared reports. History scanning is deferred until the hardened git helper of P115 exists. Commit e-mails follow P115's rules.
8. Only SaaS forges are declared hosts (api.github.com, codeload.github.com, gitlab.com, codeberg.org, registry.npmjs.org, pypi.org, hub.docker.com); self-hosted forges on org domains are target infrastructure (LIGHT/ACTIVE with scope). API only (no github.com HTML, AUP s.7); token per P111's machine-account rule; a PyPI challenge = BLOCKED.
9. Fixtures for the GitHub /orgs paths are captured from the team network before it enters the default set (the research proxy blocked them). Registry: GitHub, GitLab, npm, PyPI and Docker trusted; Codeberg community. Sources: GitHub REST 'key-terms' (as P111); GitLab, Codeberg, npm, PyPI and Docker Hub 'open'. personal_data_review covers its username inputs (A3 BR8).

Chair rationale: Approved 6-0 at median P2 on a 3-3 tie (osint_investigator, redteam_lead and legal_dpo P1) that the chair leaves at P2: it depends on the P111 client and the safe-archive helper, and the architect's sequencing floor rated it P2. legal_dpo's floor (default only for confirmed own orgs, secrets kept to the first 4 characters and never used) is stricter than P145's first4/last4 and is adopted; the architect's archive streaming replaces clones; analyst_ux's fast-inventory/deep split and redteam_lead's fork and self-hosted-forge rules are kept.
