## P278 `cdn_origin_hypothesis` - CDN origin-IP hypotheses (CloakQuest3r technique)

- council: **approved**, priority P3, default_enabled=False, provider_tier=n/a, terms=open, opsec=passive, shares_input=True
- category: pentest_recon; group: G13; inputs: domain; produces: ipv4
- auth: free_key; key env vars: V3LUM_SECURITYTRAILS_KEY; hosts: api.securitytrails.com, viewdns.info

### Final conditions (binding spec - implement every item)

1. Implemented as a correlation rule over facts other modules already produced (architect): historical A records from passive DNS (P006 SecurityTrails, P015, under their own licence and key-terms rules), certificate SAN/fingerprint matches, favicon mmh3 and title matches. It makes no network calls (disclosure 'none') and never re-queries SecurityTrails or Censys itself.
2. CDN and cloud ranges are excluded through the shared IP interval index (P169 warninglists, cloud ranges); no subdomain brute force or active resolution, and quota exhaustion of the history sources never falls back to either.
3. Scoring with explicit weights (cti_lead): certificate SAN/fingerprint match on a non-CDN IP = strong; pre-CDN historical A record = medium, decaying with age; favicon or title match = weak (phishing kits copy favicons); an IP hosting more than 50 domains = weak.
4. Output: relation origin_candidate with score and evidence, expand=False, labelled 'possible origin (hypothesis)'; never a seed for LIGHT/ACTIVE modules. For hostile sites it is an abuse-reporting aid (candidate hoster/ASN and the CDN abuse-form link).
5. No connection to candidate IPs in this build. A later verification module (https://<ip>/ with Host: <domain>) would be ACTIVE under A7 and only for IPs listed in the scope file itself, because a domain in scope does not put its old IPs in scope; never for third-party or attacker origins (BACKLOG).
6. Licences (A6): CloakQuest3r (MIT) logic adapted with a header and notice; Cloudmare (AGPL) ideas only. Opt-in (--preset deep or -M). Tests use synthetic graph fixtures (strong, medium, weak and CDN-only cases).

Chair rationale: Approved 6-0 at median P3 (osint_investigator, redteam_lead and the architect voted P2). The architect's floor turns it into a deterministic correlation rule over facts from P006/P015 and certificate/favicon modules, so legal_dpo's SecurityTrails key-terms condition is enforced where the calls happen (P006). redteam_lead's and osint_investigator's rule that historical IPs are never probed unless listed in the scope removes the active step from this build. cti_lead's weights and the hypothesis wording (analyst_ux) handle the false-positive risk; it stays opt-in. Scheduling (A16 BR1): P3 with effort M, so it is not built in this build; BACKLOG.md keeps this spec as the unblock target.

Synthesizer conditions (background; the final conditions win on conflict): Passive hypotheses only: historical A records before the CDN (SecurityTrails/passive DNS), same cert fingerprint/SAN, same favicon hash/title on non-CDN IPs (cloud_ranges to exclude CDN ASNs); score and present as hypotheses. Direct verification against a suspected origin bypasses the WAF = active probing -> separate step only with --authorized for owned assets. CloakQuest3r MIT (adapt), Cloudmare AGPL (ideas only).
Notes: Finds exposed origins of CDN-fronted sites (own assets) and attacker origins.

## P371 `saas_tenant_discovery` - Organisation SaaS tenant discovery (Okta, Atlassian, Zendesk; differential, tri-state)

- council: **approved**, priority P3, default_enabled=False, provider_tier=trusted, terms=open, opsec=passive, shares_input=True
- category: pentest_recon; group: G13; inputs: company_name, domain, keyword; produces: url
- auth: none; key env vars: -; hosts: okta.com, atlassian.net, zendesk.com

### Final conditions (binding spec - implement every item)

1. Candidates only from org_profile (brands, domain labels) or the scope file of an --authorized client engagement: at most 5 candidates per vendor per run, one anonymous GET per vendor per candidate, no permutation guessing of tenant names (redteam_lead, architect).
2. Fixed URL builders (architect): Okta https://<name>.okta.com/.well-known/openid-configuration, Atlassian https://<name>.atlassian.net/_edge/tenant_info, Zendesk https://<name>.zendesk.com/hc with redirects not followed; any other path is unreachable by construction. Okta's /.well-known/okta-organization answers for any name and is never used.
3. Rule 2: a unit test asserts no request to login, authn, signup, password-reset, user-lookup or credential-type endpoints and that no username or e-mail is ever sent. Tenant login pages are never contacted in any mode.
4. Differential decisions from the exact markers in the fixtures: Okta 200 with issuer vs 403 errorCode E0000006; Atlassian cloudId JSON vs 404; Zendesk 200 vs 301 to help-center-closed. Any other status, a generic 403, 429 or a challenge = unknown (rule 5); bodies parsed raw (not via get_json, which maps 403 to AuthRequired); a challenge stops the check (rule 1).
5. A positive is a 'candidate tenant' until corroborated by DNS verification records (P342), IdP issuer metadata or org_profile; a homonym tenant is never attributed by name alone. Tenant hosts become identity-provider attributes and pivots for passive modules only.
6. The candidate name is disclosed only to the named vendors (trusted tier), under the TLP gate. Output: one tri-state row per vendor. Opt-in (default_enabled=False).
7. Merge gate (A16): offline tests with FakeHttp (unmatched requests fail, network guard active) over trimmed real fixtures without personal data (the captured positive/negative pairs for each vendor), a provider-registry entry for every host, the registry contract test and the P327 lint.

Chair rationale: Approved 6-0 at median P3 (osint_investigator voted P3, redteam_lead P2). legal_dpo confirms it is organisation-level discovery, not account enumeration, under the rule 2 guard. The architect's construction-level URL builders and exact markers and redteam_lead's tighter candidate cap, no permutations and corroboration rule are adopted over osint_investigator's optional permutation sweep.

Synthesizer conditions (background; the final conditions win on conflict): Candidate names only from org_profile (or with --authorized for a client engagement); one request per vendor per name; differential signals only (Okta openid-configuration 200 vs 403 E0000006 - /.well-known/okta-organization answers for any name; Atlassian /_edge/tenant_info cloudId vs 404; Zendesk 200 vs 301 help-center-closed); tri-state results, challenge pages stop the check; never login, signup, reset or user-lookup endpoints (rule 2); discloses the candidate name to the vendor (TLP gate).
Notes: Attackers phish the IdP/helpdesk tenants a company uses; knowing them supports ASM and phishing simulations.
