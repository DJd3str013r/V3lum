### Final conditions (binding spec - implement every item)

1. veto_lift (1): MX-spy is removed entirely: no SMTP dialogue (EHLO/MAIL FROM/RCPT TO) with any server in any mode. Mail capability is inferred passively from DNS facts already in the graph (MX, null MX, SPF, DMARC) and shown as 'can receive mail (reply/BEC risk)'. A unit test asserts no connection to ports 25, 465 or 587.
2. veto_lift (2): the module declares opsec LIGHT (not ACTIVE), disclosure 'target', default_enabled=False, and runs only with --mode light. Per candidate it makes one GET of the homepage (plus the favicon for its mmh3), with no form submission, credential entry or download; non-HTML bodies are not parsed and are discarded.
3. Targets (A7 BR5): analyst-typed seed domains only. A seed that is itself a suspected lookalike is checked directly; for an org_profile brand seed the registered lookalikes P012 found in the same case are listed, and only those the analyst confirms (TTY; non-TTY only when supplied as seeds) become seeds, recorded in the case audit; at most 20 per run.
4. Passive first (P376): it runs after the candidate's passive results. Unregistered names, parked names (parking NS/IP), defensive registrations (registrant/NS in org_profile, or archived/urlscan evidence of a redirect to the brand) and candidates without A/AAAA records are classified without contact and never fetched.
5. veto_lift (2) / A13: lookalikes of an org brand are hostile-shaped, so the hostile-host guard refuses contact from the corporate egress unless proxy_light is configured or --egress-override "<reason>" is recorded; a refusal is BLOCKED reason_code 'hostile_host' and becomes a manual pivot.
6. Fetch through the core client only: SSRF/address guard (no private, loopback, link-local or metadata targets, AR02), manual redirects <= 5 hops re-checked by scope and guard, 2 MB cap, ua_light UA, A7 LIGHT ceilings (<= 1 req/s, <= 25 requests per host per scan), P334 LIGHT budget and the P324 hash-chained request ledger.
7. veto_lift (3): similarity comes only from ppdeep (pure-Python ssdeep, optional extra) over normalised HTML, plus title, form-action hosts and favicon mmh3 (shared helper), against the brand reference page; JavaScript is never executed. Reference: the brand seed's homepage fetched once in the same LIGHT run, or its archived copy already in the case (no third-party request here).
8. veto_lift (3): no headless browser, screenshot or pHash in this module (the architect does not approve a renderer for it); screenshots only through a separately approved capture module (P347) run by the analyst.
9. Output states per candidate: parked, defensive (never flagged), live clone (score >= threshold, a named constant), unrelated, could not verify. Wording is plain: 'page 87% similar to <brand homepage> -> likely live clone' with the matched features and compared hashes; 'lookalike / phishing-capable indicator', never 'malicious' alone.
10. veto_lift (4): the dnstwist.it web app is never used (it would learn the brand). The dnstwist-derived algorithm carries the Apache-2.0 header and a THIRD_PARTY_NOTICES entry (A6).
11. Merge gate: G13 LIGHT, so not merged or enabled before the AR20 safety suite passes (A16). Offline tests use recorded lookalike and brand pages (FakeHttp), a parked page, a defensive redirect and a hostile-guard refusal.

Chair rationale: Vetoed by legal_dpo (MX-spy is SMTP mailbox probing, rule 2); veto_lift adopted, so the item is approved and every legal_dpo lift condition is in final_conditions. All six members want page similarity and all drop MX-spy. The architect's floor shapes the build: a LIGHT module (opsec changed from active), HTML fuzzy hashing with ppdeep, no headless browser or pHash (so legal_dpo's renderer clause leaves screenshots out), a 2 MB cap and the egress guard. redteam_lead and cti_lead asked for passive classification first and a fail-closed guard, analyst_ux for the plain wording. 6. 8. takeover_verify: HTTP GET/HEAD of the in-scope name through the core client to match the provider's body fingerprint, plus a random-label wildcard probe under the same parent. 9. Forbidden (A7): claiming, registering or creating the dangling resource, and any provider API call; a unit test asserts that only GET/HEAD reach the target and no provider API host is contacted.
